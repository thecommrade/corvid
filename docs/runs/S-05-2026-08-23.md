## Results (all runtime-verified today)

1. **Identity headers on plain-HTTP serve: YES.** `tailscale serve --http=<port>` injects
   `Tailscale-User-Login` (format: the member's Google-account **email**),
   `Tailscale-User-Name` (display name), `Tailscale-User-Profile-Pic`, and
   `Tailscale-Headers-Info`, plus `X-Forwarded-For: <peer 100.x>` and `X-Forwarded-Host`.
   The HTTPS-certificates prompt did **not** fire for `--http` (R07-F23 confirmed; no CT-log
   exposure). Resolves R00-D11's `--http` UNVERIFIED.
2. **Anti-spoof: YES.** A client-sent `Tailscale-User-Login: fake@…` header was deleted and
   replaced with the genuine login.
3. **Host matching:** serve keys its mounts to `<node>.<tailnet>.ts.net:<port>` (and short
   name). A request by bare IP without a matching `Host:` header gets serve's own
   `404 page not found`. Member-facing URLs must use MagicDNS names.
4. **whois:** on the serve-proxied loopback connection (`127.0.0.1:<srcport>`, kernel mode) —
   **peer not found**; behind serve, identity must come from the headers. On a **direct**
   tailnet connection (plain socket bound to the node's 100.x, peer dialed in) —
   `tailscale whois <100.x>:<port>` **resolves** machine + user while connected. So: serve
   headers for serve-fronted apps; whois-on-source for the Caddy `forward_auth` pattern
   (R07 rec 3's default) on kernel-mode nodes. Note: the served port's inbound tailnet
   connection terminates inside tailscaled (kernel `LISTEN` socket exists on the 100.x, but
   no kernel `ESTABLISHED` conn appears for tailnet clients).
5. **Environment findings along the way (for Phase 0 / S-01):**
   - firewalld gotcha on ahnoway: `--reload` wiped the *runtime* zone binding of `tailscale0`
     mid-sequence; fix (founder): `--permanent --zone=trusted --add-interface=tailscale0`
     + reload → zone `trusted` (the mesh is the boundary, CLAUDE.md §3.2). Two stray port
     entries (50052, 5201) remain in the previously-bound zone — harmless; remove at leisure.
   - **optiplex→ahnoway tailnet data path BROKEN** while ahnoway→optiplex is direct-LAN 5 ms:
     optiplex sees ahnoway only `via DERP(iad) ~256 ms` ("direct connection not established")
     and TCP times out on every port; hub→ahnoway works. optiplex's Proton policy rules
     (`not fwmark 0xca6c lookup 51820` at prio 5209, table 51820 = `default dev protonvpn`)
     sit **above** Tailscale's rules (5210/5270) and capture tailscaled's egress. Ahnoway
     itself is clean (Tailscale rules only). Full diagnosis belongs to Phase 0 (all-pairs
     exit criterion currently fails in this direction); optiplex `wg show` + ACL paste pending.
   - Hub (solarplexus) tables recorded for Phase 0 step 2: Proton rules at 32764/65 (so
     Tailscale's 52xx rules will take priority once kernel mode is enabled), LAN bypass rule
     present, **no** 100.64.0.0/10 bypass today.
6. **Tagging observation:** identity headers and whois resolved a *user* for the hub's node —
   solarplexus is currently untagged (ADR-0002's `tag:hub` not yet applied; Phase 0 item).
