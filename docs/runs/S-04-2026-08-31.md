## What was verified (evidence, not inference)

### 1. F2 was gone, and is back — proven with unmarked traffic

The second node rebooted ~Aug 26 and lost both runtime ip rules. The VPN's own rules had been
re-created at prefs 5208/5209; CORVID's guard was absent.

| Probe | Before | After founder re-applied the guard |
|---|---|---|
| plain `ping` ahnoway → optiplex | **100% loss** (2 packets) | **0% loss** (10 packets) |
| RTT | — | **min 1.9 / avg 5.1 / max 9.5 ms** |
| ssh to the same host | worked throughout | worked throughout |

The last row is the point: **ssh and `tailscale ping` kept working the entire time the node
was unreachable for real traffic.** Both are serviced inside tailscaled. Any future run file
that cites them as reachability evidence is citing nothing. → **ADR-0008**, decision 3.

Guard as re-applied (founder, root): `ip rule add to 100.64.0.0/10 lookup 52 pref 5205` and
the v6 analogue at the same preference; both landed above the VPN's 5208/5209. **These are
runtime-only and will not survive the next reboot** until ADR-0008 is applied.

### 2. The Aug-23 failure was over-subscription, not leaked buffers

The 2026-08-23 run file blamed leaked buffers from two killed clients. That hypothesis is
**refuted by measurement**:

- **Both workers' rpc tensor caches are empty** (0 B and 4 K). The `-c` cache persists every
  tensor a worker receives. An empty cache after a failed load means the run died at *buffer
  allocation*, before a single tensor byte crossed the wire — so no prior session's leak was
  ever the constraint, and the ~155 MiB VRAM delta cited on Aug 23 was noise.
- **The exported CPU devices report total RAM as free.** With `-d Vulkan0,CPU` the workers
  advertise, from the hub: RPC1 (ahnoway CPU) 15802 MiB "free" of 15802, RPC3 (optiplex CPU)
  31890 of 31890 — i.e. *installed* RAM, ignoring what the desktop and production services
  are already using. llama.cpp's default split distributes weights in proportion to reported
  free memory (R03-F12), so it will confidently over-commit any node whose CPU device is
  exported. **This is the mechanism behind the Aug-23 refusal** and the reason `-ts` is not
  optional on a heterogeneous fleet.

### 4. Both worker ports answer from the hub, over real sockets

`nc -z` from the hub to each worker's `:50052` returned rc=0 — the honest F2-and-firewall
test, using an ordinary user-space socket rather than anything tailscaled handles. The
workers bound to their tailnet IPv4 only (`ss -tln` showed no `0.0.0.0` listener), so §5.6
bind hygiene held throughout.

### 5. The hub's link is the binding constraint — measured, not assumed

| Path | Throughput | Note |
|---|---|---|
| hub → ahnoway | **5.0 MB/s (40 Mbit/s)** | measured over the LAN, so not tailnet or crypto overhead |
| ahnoway ↔ optiplex | **16.3 MB/s (130 Mbit/s)** | 3.3× the hub — the hub's radio is the weak element, not the airtime |
| hub Ethernet | `carrier=0` | port present, cable absent (status.md finding 7, still open) |

Consequence: streaming the Q8_0 weights (28,595,763,552 B = 26.63 GiB) from the hub to the
workers is **≈ 91 minutes of saturated hub uplink** — the same link Plex and Immich serve
over. The Q4_K_M fallback (18.97 GB) is ≈ 60 minutes and saturates it just the same. There is
no arrangement that avoids this, because the weights exist only on the hub's pool: whichever
node runs the client must first obtain the file, and every route to it crosses that radio.

### 6. The client role is heavy — a Phase 1 warning worth more than tonight's number

The load attempt was launched with the plan's launcher (default load mode) and was killed
inside 90 seconds when it went wrong:

- `llama-bench` memory-maps the whole 26.63 GiB file. Against the granted `MemoryMax=8G` the
  process reached **7.87 GiB RSS** and entered uninterruptible disk wait (`D` state),
  thrashing page cache against the media pool — I/O pressure on the disks Plex reads from,
  which is precisely what decision 1 forbids.
- Network egress at that moment was ~0.6 MB/s: the process had not begun streaming to the
  workers. It was stalled on its own local I/O.
- **The correct mode exists and is documented here for next time:** `-lm dio`
  (`--load-mode <auto|none|mmap|mlock|mmap+mlock|dio>`) uses direct I/O and leaves no page
  cache footprint. `--mmap` is deprecated in favour of it at b10581. **Any CORVID client
  running on a machine that also serves media must use `-lm dio`.**
- A second launch with `-lm dio` reached the same load phase and was stopped at the founder's
  call after ~15 seconds. No allocation lines had printed; the four-buffer allocation across
  RPC devices is therefore **specified and arithmetically sound but not yet observed**.

This bears directly on **reserved ADR-0006 (topology)**: CLAUDE.md §3.2 assigns `llama-server`
to the hub, and the hub is the one node that cannot afford the client role while it is also
the media server on Wi-Fi — not because of bandwidth alone, but because model loading
competes for its RAM and its disks. **Recorded as an observation; the ADR is not written
here.**

```
  --rpc <ahnoway-100.x>:50052,<optiplex-100.x>:50052 \

  -p 128 -n 64 -r 2
```

## Gotchas recorded (new tonight)

- **`--rpc` must precede `--list-devices`** or the RPC devices silently do not appear — the
  command exits successfully having listed only local devices. Cost ~5 minutes and would have
  cost far more if the empty list had been read as "the workers aren't exporting".
- **Exported CPU devices report installed RAM as free** (finding 2). Never let the default
  proportional split see one.
- **`-lm dio` on any client that shares a machine with other services** (finding 6). The
  default (`auto` → mmap) is actively hostile to a co-tenant media server.
- **A root command over ssh may be refused by the executor's own safety tooling.** One
  `systemctl stop` on the hub was blocked; it was folded into a founder handoff instead. Plans
  should not assume an unattended root path exists just because the ssh alias does.

## Founder handoff — pending, no deadline, safe to apply any time

Both edits are inert until the next `wg-quick` cycle, so applying them disturbs nothing that
is currently running. Per ADR-0008, under `[Interface]` in each hub's `protonvpn.conf`:

```
PostUp = ip rule add to 100.64.0.0/10 lookup 52 pref 5205 2>/dev/null || true; ip -6 rule add to fd7a:115c:a1e0::/48 lookup 52 pref 5205 2>/dev/null || true
PreDown = ip rule del to 100.64.0.0/10 lookup 52 pref 5205 2>/dev/null || true; ip -6 rule del to fd7a:115c:a1e0::/48 lookup 52 pref 5205 2>/dev/null || true
```

On the second node (founder-only root): back up the conf first, edit, then confirm with a
count of matching lines (expect 2). On the always-on hub: identify the actual unit with
`systemctl list-units "wg-quick@*"` before editing, same backup-then-count.
Live test — deliberately, in a maintenance window, never during a run: restart the wg-quick
unit, then check `ip rule show` for the pref-5205 entry and confirm a plain `ping` across the
tailnet still answers.
