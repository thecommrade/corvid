## Network fixes F1/F2 (found + verified today; not in the original plan text)

- **F1 DONE (founder):** ahnoway blocked inbound UDP 41641 on its Wi-Fi zone (`public`) —
  no peer could establish inbound direct paths; opened runtime+permanent. Empirical result:
  optiplex→ahnoway upgraded from DERP(iad) ~256 ms to **direct 8 ms**; hub→ahnoway direct
  2 ms. Note from verification: the permanent rule applies on every Wi-Fi network this
  roaming laptop joins — acceptable (WireGuard drops unauthenticated packets), recorded.
- **F2 (optiplex) — diagnosis adversarially verified** (3-agent workflow, 2026-08-23; full
  verdicts + citations preserved in the session workflow output; key sources: ip-rule(8),
  wg-quick source lines 224-225, tailscale netns_linux.go/router_linux.go, RFC 6598,
  tailscale KB 1082/1105, Proton Linux split-tunneling docs):
  - CONFIRMED: Proton's wg-quick rules land at 5208/5209 (kernel assigns lowest−1 under
    Tailscale's 5210), so unmarked traffic to 100.64.0.0/10 falls through to
    `table 51820 → default dev protonvpn` and is black-holed; Tailscale's rules are dead
    code while Proton is up. tailscaled's own 0x80000-marked packets ride Proton for
    WAN/DERP and escape via the LAN rule for LAN endpoints.
  - **REFUTED (our earlier claim): "optiplex still works as an inbound-dialed worker."**
    Rule 5209 matches by destination — kernel-TCP replies to any 100.x peer die in Proton
    too. Only tailscaled-internal services (Tailscale SSH, disco) work inbound over tailnet
    addresses. **Until F2 is applied, optiplex cannot serve tailnet-addressed traffic at
    all — F2 is a hard prerequisite for S-04's optiplex worker.** (Our "ssh optiplex works"
    evidence rode the LAN: the ssh config's first matching block pins the LAN address.)
  - Fix form: `ip rule add to 100.64.0.0/10 lookup 52 pref 5205` **plus** the v6 twin
    (`to fd7a:115c:a1e0::/48` — Proton also claims `::/0` and MagicDNS returns AAAA).
    Captures nothing beyond tailnet routes (table 52 holds only tailnet /32s; non-tailnet
    CGNAT destinations fall through to Proton unchanged — RFC 6598 makes them illegitimate
    on this LAN anyway).
  - **Verified failure mode:** any Proton reconnect re-adds wg-quick rules at lowest−1
    (they would land at 5203/5204, above ANY static pref) — so the runtime rules are a
    session fix only. Durable form: `PostUp`/`PreDown` in the wg-quick config's
    `[Interface]` section (optiplex runs `wg-quick@protonvpn.service`) or an NM dispatcher
    hook; **needs an ADR** (no vendor-supported Tailscale+Proton coexistence recipe exists
    on Linux). Same race applies to the hub post-kernel-mode → same durable fix there.
  - Status: founder applying the runtime rules now; retest + S-01 optiplex tailnet legs
    follow.
