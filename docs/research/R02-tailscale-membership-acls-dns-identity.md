> DOSSIER R02 — Tailscale: membership, ACLs, DNS, identity (verified 2026-08-22 against tailscale.com KB pages, the pricing page, and tailscale/tailscale at tag v1.102.3, released 2026-08-20). 1. MEMBERSHIP AND PLAN LIMITS. The current free Personal plan is "$0 Free forever", "Up to 6 users", "Unlimited user devices", "Up to 3 ACL groups", "Up to 50 tagged resources to start" (F1, F5). Tailnets created with a public-domain login (Gmail, Apple, personal GitHub) are auto-enrolled in Personal; the plan is non-commercial only (F2). Seats are counted per user, not device; an invited user only occupies a seat on first admin-console login or first device authentication (F4). The old 3-user Personal and 6-user Personal Plus plans are legacy; new Personal = 6 (F3). Two ways to bring a friend in: (a) a one-time URL "Invite any user" (the mechanism for shared-domain/personal tailnets; friends sign in with any IdP or passkey; invites expire in 30 days; available on all plans) — the friend becomes a full tailnet member and is covered by autogroup:member (F6, F7, F8); (b) node sharing — share a specific machine (e.g. solarplexus) with a user on another tailnet; the recipient gets "access to only the shared machine in your tailnet, and nothing else" (F9). Sharing is quarantined/one-directional by default: the shared machine can receive connections from the recipient but cannot initiate them; mutual sharing is possible by sharing in both directions (F10). The sharer learns the recipient's email and avatar, can write ACL rules against the recipient's email or autogroup:shared, tags/groups/subnets are stripped, only users (not tags) can accept, and the recipient must be Owner/Admin/IT admin of a tailnet (every fresh personal login creates one) (F11). Shared machines must be addressed by FQDN hostname.tailnet-name.ts.net, never the short name (F12). Crucially for zero-login, Serve identity headers ARE populated for external users who accepted a share (F13). Shared users are NOT autogroup:member (F8). Practical reading for CORVID: up to 6 full members (founder + 5) get short names, SSH, tags, full ACLs; everyone beyond that can be a *consumer* via a shared solarplexus with identity headers, but cannot easily be a *contributor* without mutual sharing, because the hub cannot open connections to them (F10). 2. ACLs, TAGS, SSH POLICY. A new tailnet's policy allows all; once an "acls"/"grants" section exists the model is deny-by-default, directional, enforced on each device; grants are the recommended syntax (F14). Tags are service-account identities: applying a tag removes user identity, a tagged device must keep at least one tag, tag ownership is declared in tagOwners, and tagged devices can only SSH into other tagged devices; all plans include 50 tagged devices (F15). The SSH policy section has action "accept" \| "check", src, dst, users, checkPeriod, acceptEnv; checkPeriod default 12h (1 min–168 h or "always"); check mode itself is on all plans but a NON-default checkPeriod and localpart:*@domain user mapping require Premium/Enterprise (F16, F19). The default SSH rule is check-mode, autogroup:member → autogroup:self, users [autogroup:nonroot, root]; a destination host must still opt in with `tailscale set --ssh`; editing the ssh section overrides the default (F17). Allowed SSH shapes: user→own devices, user→tagged device, user→shared tagged device, tagged→tagged (never check mode). Server side only on Linux and the open-source macOS tailscaled; it claims port 22 only on the Tailscale IP, leaving sshd untouched (F18). 3. DNS. MagicDNS is on by default for tailnets created on/after 2022-10-20, needs no nameserver on v1.20+, gives machine-name.tailnet-name.ts.net and auto-adds the tailnet search domain; per-device opt-out is `tailscale set --accept-dns=false` (F20). By default devices keep their local DNS settings and only use tailnet nameservers when needed; "Override DNS servers" forces the global nameservers; a restricted nameserver (split DNS) answers only its domain; resolver order is not guaranteed, so a LAN resolver with different answers should be added as split DNS for its domain, not as a global nameserver (F21). On Linux, Tailscale tries to cooperate with whatever DNS system exists; with NetworkManager + systemd-resolved, /etc/resolv.conf must symlink to /run/systemd/resolve/stub-resolv.conf; without a DNS manager tailscaled and dhclient fight over resolv.conf; Tailscale's own resolver is 100.100.100.100 (F22). `--accept-dns` defaults to true; `--hostname` changes the MagicDNS name (F23). 4. KEY EXPIRY. Default 180 days, configurable 1–180, per-device "Disable Key Expiry" in the admin console; first-time tagged devices get expiry disabled by default; `tailscale up --force-reauth` renews; admins can "Temporarily extend key" for 30 minutes on an expired device (F24, F15). 5. IDENTITY: SERVE HEADERS VS WHOIS. `tailscale serve` proxies tailnet traffic to a local service, requires HTTPS certs enabled, honours ACLs, and injects exactly three headers — Tailscale-User-Login, Tailscale-User-Name, Tailscale-User-Profile-Pic — after stripping any incoming copies; not for Funnel traffic and not populated for traffic from tagged devices; values may be RFC2047 Q-encoded; Tailscale's stated best practice is that the backend listens on localhost only so nobody can reach it bypassing Serve (F25). v1.92+ can also forward Tailscale-App-Capabilities via --accept-app-caps (F25). Serve CLI: `tailscale serve [--bg] [--http\|--https\|--tcp\|--tls-terminated-tcp=<port>] [--set-path] [--yes] <target>`, `serve status`, `serve reset`, `... off` (F26). HTTPS prerequisites: MagicDNS on, "Enable HTTPS" acknowledged (machine names + tailnet DNS name go to public CT logs), `tailscale cert` obtains Let's Encrypt 90-day certs that YOU must renew when delivered as files; tailnet name cannot be changed later except default↔random (F27). `tailscale whois ip[:port]` returns Machine {Name, ID, Addresses, AllowedIPs}, User {Name = owner email

## Recommendations for the spec

1. Membership tiers (feed ADR 0002): the founder's Personal tailnet holds at most 6 users (F1). Use URL 'Invite any user' (F6) for the founder + up to 5 contributing friends — they become autogroup:member (F8), get short MagicDNS names, Tailscale SSH, tags and full ACL targeting. Everyone beyond that is a *consumer* reached via node-sharing of solarplexus only (F9); they must use the FQDN (F12), appear as autogroup:shared (F8), still get Serve identity headers for zero-login (F13), but the hub cannot open connections to their machines (F10), so a share-only friend cannot be a compute contributor without mutual sharing. Decide explicitly who is a member vs a sharee.
2. Zero-login design: put every member-facing web app behind `tailscale serve` on solarplexus (F25, F26), have backends listen on 127.0.0.1 only, and trust exactly the three headers Tailscale-User-Login / Tailscale-User-Name / Tailscale-User-Profile-Pic (F25). For non-HTTP services (llama.cpp RPC, the agent's API) and for defence in depth, resolve the peer IP with `tailscale whois --json` (F28). Treat header values as possibly RFC2047 Q-encoded (F25).
3. Hub networking contradiction: solarplexus runs tailscaled in userspace mode, so there is no Tailscale interface to bind to and inbound tailnet TCP is forwarded to 127.0.0.1:<port> (F32); the CLAUDE.md §3.2 rule 'rpc-server binds to the Tailscale interface only' cannot be implemented there, and anything on loopback is tailnet-reachable. Either (a) move solarplexus to kernel/TUN mode (root tailscaled; better performance, F31) and keep the bind-to-tailscale-IP rule, or (b) restate the rule for userspace nodes as 'listen on 127.0.0.1, never 0.0.0.0, and gate ports with grants'. Write this into the topology ADR.
4. Spike before Phase 1 (F39, F40): on solarplexus verify `tailscale serve`, the Tailscale SSH server, and rpc-server reachability all work in userspace mode; record results in docs/runs/. If any fail, that decides (a) above.
5. Tags for infrastructure only: tag solarplexus and always-on workers (e.g. tag:corvid-hub, tag:corvid-worker) via tagOwners; their key expiry is disabled by default (F15, F24), which is what an unattended hub needs. Never tag friends' laptops (tagging removes user identity and tagged devices cannot SSH into user devices; identity headers are not populated for tagged sources) (F15, F25).
6. Key expiry policy: user devices expire every 180 days by default (F24); tell members they will re-authenticate roughly twice a year; disable expiry only on tagged infrastructure; document the admin 'Temporarily extend key' 30-minute rescue for an expired remote box.
7. SSH policy on Personal: keep check mode at the default 12 h (changing checkPeriod needs Premium, F16/F19); add an accept or check rule src founder → dst tag:corvid-* users [root, autogroup:nonroot] plus the matching grants port-22 rule (F17, F18); tagged→tagged SSH cannot be check mode (F18). Server side is Linux and open-source macOS tailscaled only (F18), so Windows friends are SSH clients, never servers.
8. DNS: keep MagicDNS on (default, F20) and do NOT enable 'Override DNS servers' (F21). If a LAN resolver (Pi-hole, router) must answer a local domain, add it as a restricted (split-DNS) nameserver for that domain rather than a global one (F21). On Linux build nodes ensure /etc/resolv.conf -> /run/systemd/resolve/stub-resolv.conf when systemd-resolved + NetworkManager are present (F22); debug with `tailscale dns status`.
9. HTTPS/Serve prerequisites: before enabling HTTPS, choose final machine names and a randomised tailnet DNS name (both are published to CT logs and the tailnet name cannot be changed later except default<->random) (F27). Serve auto-provisions its own certs; anything issued with `tailscale cert` you must renew yourself every 90 days (F27).
10. Zero-public-exposure CI check: Funnel is enabled by default at the tailnet level (F36); add `tailscale funnel status` (must be empty) and `tailscale serve status` review to the no-0.0.0.0 check, and consider removing the `funnel` nodeAttr from the policy file.
11. Operator: run `tailscale set --operator=<user>` on founder/member Linux boxes so the CORVID agent and CLI can call tailscaled without sudo (F29); `tailscale set` is idempotent per flag, unlike `tailscale up` which needs every flag repeated (F23, F29).
12. Pin client v1.102.3 (released 2026-08-20, F35) as the reference version for CLI syntax (Serve CLI changed at 1.52; app-caps header at 1.92; acceptEnv at 1.76) and record it in the §4 credit row; Headscale v0.29.3 (BSD-3) stays the documented escape hatch (F34).
13. Member-facing copy: sharees see the shared machine listed as owned by the sharer and must type the full name host.tailnet.ts.net (F11, F12) — put that exact FQDN on the onboarding index card.

## Open questions

- What does `tailscale whois` report (User.Name/ID) for a connection from a node-share recipient on another tailnet — their login email, or nothing? (F38) Test once the first friend is shared in.
- Do `tailscale serve` and the Tailscale SSH server function on solarplexus while tailscaled is in --tun=userspace-networking mode? (F39, F40) Decides whether the hub must move to TUN/kernel mode.
- Can a share-only friend contribute compute at all, i.e. does mutual sharing (friend shares their rpc-server box back to the founder) work in practice, and is it acceptable UX for a non-technical friend who is Owner of their own auto-created tailnet? (F10, F11)
- How many of the ~20 friends in §10 need to be full members (≤6 incl. founder) versus sharees? The 6-user cap forces a tiering decision before Phase 0 invites go out. (F1)
- Does the pricing table's 'Basic Tailscale SSH' cell for Personal (check mark, vs 'Up to 5 hosts' on Standard) really mean unlimited SSH hosts on Personal? The Personal highlights say 'Try SSH and Kubernetes features'. Verify in the admin console. (F19)
- Is any LAN resolver in use on the build nodes today (Pi-hole/router DNS) that would need a split-DNS restricted nameserver, or is MagicDNS alone sufficient? (F21, F22)
- Tailscale says it is currently not enforcing ACL-group/tagged-resource limits (F4); what is the date when enforcement begins, and will 3 ACL groups suffice for CORVID's policy design?
- Before enabling HTTPS: which machine names and which tailnet DNS name are acceptable to publish in Certificate Transparency logs? (F27)

**Completeness critic — missing for a plan writer:**

- Outbound from a userspace-networking hub: F30-F32 cover inbound loopback forwarding only. How does a host process on the hub open outbound TCP to tailnet peers (llama-server --rpc worker:50052, ssh to workers, agent callbacks) when the app has no SOCKS5/HTTP-proxy support? Is the only path the SOCKS5 proxy via proxychains/socat, `tailscale nc`, tsnet, or leaving userspace mode? Phase 1's hub-to-rpc-server topology hinges on this and the dossier is silent.
- Why the hub runs in userspace mode and what kernel mode needs (/dev/net/tun present, CAP_NET_ADMIN, LXC/Docker device passthrough) is not recorded, so the plan cannot choose between 'fix the hub' and 'design around userspace'.
- MagicDNS on a userspace node: F20-F22 assume a tun interface and 100.100.100.100. Does MagicDNS resolution work for host processes on a --tun=userspace-networking node, and does the SOCKS5 proxy resolve MagicDNS names itself?
- F39 and F40 (Tailscale SSH server and `tailscale serve` on a userspace node) are left unverified; a live test on the hub (`tailscale set --ssh`, `tailscale serve 3000`, `tailscale serve status`) would settle both and is not recorded.
- Programmatic zero-login: only the `tailscale whois` CLI form is documented (F28). Missing: the LocalAPI whois endpoint over /var/run/tailscale/tailscaled.sock (or tsnet), the `--json` field names (UserProfile.LoginName/DisplayName/ProfilePicURL, Node.Name, Node.Tags, CapMap), and whether a Serve-proxied request carries the client's tailnet IP (X-Forwarded-For) so a backend can call whois for node-level identity, since the Serve headers carry user identity only and no node name.
- F38 unverified: what whois returns (User.Name) for traffic from a node-share recipient, and under which login share recipients appear in `tailscale status` / the admin console. Testable today on the existing Zach share.
- Seat accounting for sharing: does a user who only accepts shares (never invited) count toward the 6-user Personal cap? F5 implies not but never states it. Is there a cap on outbound shares/recipients per machine, and does a friend accepting shares into their own Gmail tailnet count under the 'multiple tailnets' limit F4 says is unenforced? This decides whether '6 members + shares' reaches ~20 friends.
- What the `--operator` user may do (F29 only defines the flag): can the operator run `tailscale serve`, `whois`, `set --ssh`, `up`, `cert`, and LocalAPI calls? Needed to run CORVID services as a non-root service account on the hub.
- ACL authoring specifics are absent: exact `acls` rule syntax (action/src/dst with host:port, port ranges, proto), `tagOwners` declaration for tag:corvid-hub / tag:corvid-worker and who may apply them, the `grants` syntax Tailscale now recommends (src/dst/ip/app) and whether grants + app capabilities are available on Personal, and the `tests`/`sshTests` sections. F14-F17 give defaults and semantics only.
- Funnel hardening: F36 says Funnel is 'enabled by default' and 'can be turned off' but not how (nodeAttrs `funnel` in the policy file vs admin console), whether a fresh default policy already grants `funnel` to autogroup:member, or how to verify it is off (`tailscale funnel status`). §5.6 zero-public-exposure needs the exact switch.
- Serve operational details: does `tailscale serve` auto-provision and auto-renew its Let's Encrypt cert (F27 only says `tailscale cert` certs are operator-renewed)? Does `--http=<port>` still require HTTPS enabled on the tailnet? Does `--bg` config persist across tailscaled restart/reboot? Are identity headers added on plain-HTTP and not on `--tcp` listeners? Does Serve pass SSE/streaming token responses unbuffered?
- Auth keys are only mentioned in passing (F15): types (reusable/ephemeral/pre-authorized/tag-bound), the max 90-day key expiry, availability on Personal, and whether `tailscale up --auth-key ... --advertise-tags` is the right way to enroll tagged hub services non-interactively.
- Member-role visibility and join controls: what a Personal-tailnet 'Member' (F19) can see in the admin console (all machines, other members' emails, the policy file), and whether device approval can be enabled so no new device joins without admin sign-off. Needed for the honest privacy note (§5.7) and 'nothing joins by default'.
- Membership lifecycle: what happens to a removed member's devices (including tagged devices they enrolled), and whether a member can leave a tailnet on their own; F11 covers only deletion of the shares they manage.
- Headscale parity for the escape hatch (F34/F35 give licence and version only): does Headscale support node sharing, grants, Serve HTTPS certs and identity headers, Tailscale SSH policy, and ts.net-style MagicDNS names? Without this the '6 users or Headscale' decision cannot be written. (May belong to another dossier; if so, cross-reference it.)
- Per-platform CLI availability for the mixed fleet: which of `tailscale set --operator`, `serve`, `whois`, and `--accept-dns` exist on the macOS App Store vs standalone vs open-source variants and on Windows; F18 only settles the SSH server (Linux/macOS OSS). Matters for the per-OS member guides.
