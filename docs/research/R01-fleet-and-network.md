TAILSCALE CONNECTION MODEL (what the plan can assume). Tailscale offers three connection types — direct (UDP peer-to-peer), DERP-relayed, and Peer-Relay (another tailnet device relays) — all end-to-end WireGuard-encrypted; "the primary difference between them is performance, not security" (F1). Every connection STARTS relayed via DERP and is upgraded to direct if NAT traversal succeeds; otherwise it tries a peer relay, otherwise stays on DERP and periodically re-checks (F2). DERP servers have "limited QoS", are "generally slower than direct connections and may offer lower maximum throughput", and being relayed when direct was possible "is one of the most common causes of performance issues" (F3). DERP cannot read traffic (F4). Clients pick the lowest-latency DERP region; the US has 10 regions (F5). 2. WHEN HOME NETWORKS GET RELAYED. Tailscale's official connectivity matrix (KB 1411): No-NAT+anything → Direct; Easy+Easy → Direct; Easy+Hard → Relayed; Hard+Hard → Relayed (F6). Easy NAT = full-cone NAT / UPnP, NAT-PMP or PCP available / hairpinning / consistent port mapping. Hard NAT = per-destination port mapping with unpredictable external ports. NOTE: KB 1257 says only "Tailscale can't establish a direct connection if both devices are behind a hard NAT", and the 2020 NAT-traversal blog says the birthday-paradox trick gets through ONE hard NAT — the KB pages are not fully consistent; plan conservatively per the 1411 matrix and measure (open question). Tailscale's own 2020 blog: "home routers tend to be easy NATs"; under CGNAT, port-mapping protocols don't help across the carrier box, and two peers behind the same CGNAT need the ISP box to hairpin — "If both hairpinning and port mapping protocols fail, you're stuck with relaying" (F14). Tailscale IPs themselves come from the CGNAT range 100.64.0.0/10 (F13). 3. HOW TO IMPROVE ODDS OF DIRECT (what to put in the member setup guide). Enable NAT-PMP or UPnP on the home router; or open/forward UDP 41641 on the public IP ("ensures a direct connection from any peer device, where possible"); port changeable via tailscaled --port (F7). Firewall egress needed: TCP *:443 (control + DERP data), UDP from :41641 to *:*, UDP *:3478 (STUN), optional TCP *:80 (F8). Peer Relays (Tailscale ≥1.86, any OS except iOS/tvOS/Android, needs one reachable UDP port, `tailscale set --relay-server-port=N` + a `tailscale.com/cap/relay` grant) are "usually faster than DERP" but still slower than direct (F11). 4. WHAT `tailscale netcheck` / `status` / `ping` FIELDS MEAN (S-01 must record these per node). netcheck: UDP (false ⇒ will rely on DERP), IPv4/IPv6 public endpoints, MappingVariesByDestIP ("the most important field" — true ⇒ hard NAT), HairPinning, PortMapping (UPnP/NAT-PMP/PCP; false ⇒ "device likely cannot use direct connections"), Nearest DERP + per-region DERP latency (F9). status column 5: "active; direct <ip:port>" vs 'active; relay "<city>"' vs "peer-relay <ip:port>:vni:<id>"; JSON: `tailscale status --json \| jq '.Peer[].Relay'`. ping: lines read "via DERP(nyc) in 130ms" until a direct path appears as "via <ip:port> in 35ms"; `--until-direct` defaults true; otherwise ends "direct connection not established" (F10). 5. USERSPACE-NETWORKING MODE ON THE HUB — A TOPOLOGY PROBLEM. KB 1112: with `--tun=userspace-networking` there is no TUN interface; tailscaled "functions as a SOCKS5 or HTTP proxy which other processes ... can connect through"; apps must be pointed at ALL_PROXY/HTTP_PROXY; the mode is "primarily for serverless environments" (F12). Tailscale source (v1.102.3 netstack.go) shows inbound TCP to the node's Tailscale IP on port P is dialed to 127.0.0.1:P on the host (F12b). Meanwhile llama.cpp's RPC client dials workers with a plain TCP connect() and has no proxy support (F20). Consequence: on solarplexus as currently configured, llama-server `--rpc 100.x.y.z:50052` CANNOT reach workers (outbound 100.x traffic has no route without TUN), but an rpc-server on solarplexus bound to its default 127.0.0.1:50052 IS reachable from peers (inbound gets forwarded to loopback). CLAUDE.md §3.2 assigns llama-server to solarplexus — that assignment needs either TUN mode on the hub or role inversion. This is the single most important finding for the topology ADR. 6. ## Recommendations for the spec

1. TOPOLOGY ADR (reserved 0006): resolve the userspace-mode conflict on solarplexus before Phase 1. Facts F12+F20 mean llama-server on the hub cannot dial `--rpc 100.x:50052` workers today. Options to weigh in the ADR: (a) switch solarplexus tailscaled to kernel TUN mode (preferred if /dev/net/tun is available — then it can bind services to its 100.x IP and be a candidate peer relay); (b) invert roles: run llama-server (the RPC client) on a TUN-mode node (e.g. the RTX 2070 Super laptop) and run ggml-rpc-server on solarplexus at its default 127.0.0.1:50052, which peers reach via netstack's inbound→loopback forwarding; (c) bridge with `tailscale nc`/socat per worker (fragile, last resort).
2. Binding rule for §5.6: ggml-rpc-server binds to the node's Tailscale IP (100.x) on TUN-mode nodes, never 0.0.0.0; on userspace-mode nodes leave the default 127.0.0.1 (inbound arrives via tailscaled). Keep upstream's own warning text ('Never expose the RPC server to an open network!') in the runbook; add a CI/agent check that rejects `-H 0.0.0.0`.
3. Spike S-01 protocol must record per node pair: `tailscale netcheck --format=json` (UDP, MappingVariesByDestIP, PortMapping, Nearest DERP + latency table), `tailscale ping --until-direct` outcome and steady RTT, `tailscale status --json` `.Peer[].Relay`/`CurAddr`; then ggml-rpc-server decode tokens/s and ms/token for: same-LAN wired, same-LAN Wi-Fi, cross-house direct, and (if obtainable) cross-house DERP-relayed. Count blocking round trips per token with GGML_RPC_DEBUG=1 to calibrate F24.
