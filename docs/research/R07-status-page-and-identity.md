> # R07 — Status page & identity - **Depth:** full - **Written:** 2026-08-22 by research agent (Fable) · **Verified:** 2026-08-22 (adversarial pass: pending) - **Feeds:** Phase 2 spec (status page v0 at `:8092`, identity dependency of the coordinator API), ADR-0003 (Caddy front door), ADR-0002 (tags vs identity), S-05 (serve headers), R06 (heartbeat interval → node-down threshold) ## Purpose Decide (a) Grafana vs a simple server-rendered page for the Phase 2 "live map of the co-op"; (b) how a member's Tailscale identity reaches CORVID web apps behind Caddy on the hub — and what changes when the hub's tailscaled runs in userspace mode, as solarplexus does today; (c) Caddy basics (`reverse_proxy`, `handle_path`, `bind`, `forward_auth`, `log`, config location) and licences; (d) what the live map must show per ADR-0001 and the Phase 2 acceptance numbers. ## Headline findings (the plan writer should read these first) 1. **Grafana is AGPL-3.0-only at v13.2.0** (with Apache-2.0 sub-packages); Grafana Labs' own Enterprise image is *proprietary* though "free". OSS Grafana has every panel the map needs (Stat, Gauge, Table, State timeline, Status history, Node graph, Canvas) and a built-in PostgreSQL data source — but it brings a second identity system (`[auth.proxy]`/anonymous), phone-home defaults (`reporting_enabled`, `check_for_updates` both true), binds `0.0.0.0` by default, and cannot guarantee "thanks, never ranks" (any table can be sorted). **Recommendation: status page v0 = a small server-rendered page** (FastAPI + Jinja2, optional htmx polling) reading Postgres; Grafana is a Phase 4 option for history/thank-you board if wanted. 2. **Identity, two mechanisms, both verified at tailscale v1.102.3 source:** `tailscale serve` injects `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-User-Profile-Pic` into proxied requests and *deletes* any incoming header of the same name (anti-spoof); headers are **not set for traffic from tagged nodes** and not set for Funnel. `tailscale whois ip[:port]` (CLI or LocalAPI `/localapi/v0/whois?addr=`) resolves a connecting address to node + user; on Linux any local user can call it (read-only LocalAPI over the 0666 unix socket `/var/run/tailscale/tailscaled.sock`). 3. **Userspace mode changes the wiring (matters today on solarplexus):** an inbound tailnet TCP connection to the node's own 100.x IP is rewritten by tailscaled's netstack to a dial of `127.0.0.1:<port>` on the host, and tailscaled registers that loopback `ip:srcport` → peer mapping so `whois 127.0.0.1:<srcport>` still resolves the peer. Consequences: services must listen on loopback (binding the tailnet IP is impossible — there is no `tailscale0`), they see `127.0.0.1` as the client, and whois must be called with **ip:port** (exactly what `tailscale nginx-auth` and Caddy's documented `forward_auth` Tailscale example pass via `Remote-Addr`/`Remote-Port`). In kernel mode (planned for solarplexus, finding 10) the app sees the real 100.x source and may bind the tailnet IP. 4. **Caddy is Apache-2.0 at v2.11.4.** `reverse_proxy` passes `Host` through and sets `X-Forwarded-For/Proto/Host` (ignoring incoming ones unless `trusted_proxies`); `header_up -Name` deletes a request header; `handle_path /x/*` = `handle` + `uri strip_prefix`; `bind <ip>` pins the listener; `forward_auth` grants on 2xx and `copy_headers A>B` renames identity headers for the app — Caddy's docs ship a Tailscale example for exactly this; `*.ts.net` certs come from local tailscaled (needs the tailnet HTTPS feature and `TS_PERMIT_CERT_UID=caddy`). Access logs redact Cookie/Authorization by default. Linux package: `/etc/caddy/Caddyfile`, `systemctl reload caddy`, admin API `localhost:2019` (the hub already listens on 2019 — R00-F7). `import conf.d/*` lets CORVID drop in its own route file. 5. **ADR-0002's `tag:member`** on machines members *also browse from* would strip serve identity headers and make whois return tags instead of a user. Tag only servers; keep members' consuming devices user-owned. 6. **HTTPS on the tailnet publishes `solarplexus.tail2990fc.ts.net`-style names to public CT logs** (Tailscale's own warning). `tailscale serve` has a `--http=<port>` flag (serve only, not funnel) and the HTTPS-feature prompt is only triggered for the HTTPS serve type (source), so plain-HTTP serve with identity headers is plausible — **S-05 must confirm at runtime**. ## Facts See the structured `facts` list (R07-F1 … R07-F38). ## Main-session notes

- Required panels per ADR-0001: pool capacity, utilisation, distance to the next product threshold; contributions appear only as thanks — never counts or ranks.
- Identity: `tailscale serve` headers (R00-D11) vs `tailscale whois` — S-05 decides which the Phase 1/2 specs use.

## Recommendations for the spec

1. Status page v0 = a server-rendered page, not Grafana: FastAPI + Jinja2 (deps already chosen by R06 for the coordinator) serving `/status` at :8092, re-rendered every 5–15 s (meta refresh or htmx 0BSD polling). Rationale: ADR-0001's four panels are bespoke (threshold distance, thanks-without-numbers), the page must never offer a sortable per-member table, and Grafana adds AGPL, a second identity system, `0.0.0.0` and phone-home defaults (R07-F8) to a 16 GB hub shared with Plex/Immich. Keep Grafana as a Phase 4 option for time-series history; if adopted: image `grafana/grafana` (OSS, AGPL — not the proprietary enterprise image), GF_SERVER_HTTP_ADDR=127.0.0.1 (or tailnet IP), GF_ANALYTICS_REPORTING_ENABLED=false, GF_ANALYTICS_CHECK_FOR_UPDATES=false, GF_AUTH_ANONYMOUS_ENABLED=true org_role Viewer, GF_AUTH_DISABLE_LOGIN_FORM=true, optional [auth.proxy] fed by Caddy header_up from the identity header with whitelist=127.0.0.1, a SELECT-only Postgres role, dashboards provisioned as JSON from `deploy/grafana/`, and a §4 row (AGPL-3.0-only, Grafana Labs) in the same commit.
2. Live-map data contract (for R06's schema and the page): per node — name, owner display name, last_heartbeat_at, age = now() − last_heartbeat_at, state = live (age < 1×interval) / stale (< 3×) / down (≥ 3×), and only the opted-in capabilities (offers, cpu cores, ram_gb, gpu name + vram_mb, battery/idle flags) under the owner's slider caps. Pool capacity = Σ over live nodes of offered (capped) RAM/VRAM/cores; utilisation = currently assigned/used by CORVID work; thresholds = a small `product_threshold` table (product, metric, needed) so 'distance to next threshold' is `needed − current` rendered as a progress bar; thanks = alphabetical list of contributor names with no numbers, no order by amount, no per-member usage. No geo map of houses (privacy); the 'map' is logical. Page shows a 'stale data' badge when the last successful DB read is older than 2× the refresh.
3. Identity plumbing — decide by hub Tailscale mode and keep backends loopback-only: all CORVID backends (8090–8093) bind 127.0.0.1 on the hub; Caddy is the only tailnet-facing listener (`bind <tailnet IP>` in kernel mode; `bind 127.0.0.1` while solarplexus is in userspace mode, where tailscaled forwards inbound 100.x:80 → 127.0.0.1:80 — R07-F26). Preferred identity mechanism: a tiny CORVID `whoami` forward_auth endpoint (Python, ~30 lines) that runs `tailscale whois --json {remote_host}:{remote_port}` (or the LocalAPI whois over the unix socket) and returns Tailscale-User/Login/Name headers, wired exactly like Caddy's documented Tailscale forward_auth example (R07-F15, R07-F29). It works in both tailscaled modes, needs no HTTPS feature (no CT-log disclosure, R07-F19), and depends on nothing experimental. Alternative A: `tailscale serve --bg --http=80 http://127.0.0.1:<caddy>` (Serve injects headers and strips squatters, R07-F22/F23) — adopt only if S-05 shows headers on --http; Alternative B: Serve on https:443 (requires enabling HTTPS certs; accept CT-log exposure of `solarplexus.<tailnet>.ts.net`). In every variant Caddy must `header_up -Tailscale-User-Login` (and siblings) on the route *before* forward_auth/serve re-adds them, so a member cannot self-assert identity; and ADR-0002's ACL should expose only Caddy's port(s) to members, never 8090–8093.
4. ADR-0002 amendment: `tag:member` must not be applied to devices a member browses from — tagged nodes get no serve identity headers and whois returns tags, not a user (R07-F21/F22/F24). Tag hubs only; members' laptops/phones stay user-owned. If a member's contributing desktop is also their browsing device, leave it untagged and express the ACL in terms of users/autogroup:member instead.
5. Caddy integration on the hub: CORVID ships `deploy/caddy/corvid.caddy` (site block or snippet with `handle_path`/`handle` routes for /, /chat, /v1, /api, /status plus the forward_auth block) and the Phase 2 plan installs it via an `import` line in the existing Caddyfile (R07-F20), then `systemctl reload caddy` (or `docker exec caddy caddy reload` if the hub's Caddy is a container — open question). Use `handle /status/*` if the status app is mounted at /status, `handle_path` only for apps that expect to be at root (R07-F14). Leave the existing media-stack routes untouched. Access logs: default redaction is fine (R07-F17); never enable `log_credentials`; no request bodies are logged by Caddy.
6. S-05 scope (tighten the card): on ahnoway (kernel mode) and, once Phase 0 steps land, on solarplexus (userspace mode): (1) `tailscale serve --bg --http=8099 http://127.0.0.1:<echo>` — do identity headers appear? (2) `tailscale serve --bg --https=443 …` — same, and note whether the tailnet HTTPS prompt fires; (3) connect directly to 100.x:<echo> on the userspace hub and record the source IP/port the echo server sees; (4) `tailscale whois --json 127.0.0.1:<that port>` while the connection is open — does it resolve the peer? (5) repeat (3)/(4) after solarplexus is switched to kernel mode. Record exact header names and values (Login may be an email or `user@github`).
7. Lightweight alternatives — what they are good for: Gatus (Apache-2.0) as an optional zero-code *service* health page (HTTP checks of /v1/models, /api/health; external endpoints pushed by agents) if the founder wants uptime history without writing it; Beszel (MIT) only as a design reference for per-host metrics incl. NVIDIA/AMD/Intel GPU (its hub port 8090 collides with ADR-0003 if co-hosted); Perses does not read SQL (skip); Uptime Kuma is uptime-only (skip); Metabase is a heavier AGPL BI UI (skip for v1). None replaces the ADR-0001 panels.
8. Log policy carried over from R06: the status page and whoami endpoint log only metadata (timestamp, path, status, latency, node id) — never identity header values in the access log beyond what Caddy logs by default, never query strings containing member names, never bodies.

## Open questions

- Will solarplexus be switched from userspace to kernel mode before Phase 2 (status finding 10)? It decides bind strategy (tailnet IP vs 127.0.0.1) and whether whois needs ip:port.
- S-05: do identity headers appear on `tailscale serve --http=<port>` (source says the Rewrite hook is shared, KB is silent)? Does Serve run at all on the userspace-mode hub at 1.98.4 / 1.102.3? What exact LoginName format do members get (email vs `user@github`)?

- Is `tailscale nginx-auth` packaged for Ubuntu 24.04 (tailscale-nginx-auth)? (Only matters if the team prefers it over a CORVID whoami endpoint.)
- Heartbeat interval (R06): 15 s → node-down at 45 s? The status page's stale/down colours depend on it.
- If Grafana is adopted later: measure its RAM/CPU on the 16 GB hub next to Plex/Immich before committing; confirm the OSS image tag to pin (v13.2.0 today).
- Member device tagging in ADR-0002's ACL baseline vs identity headers — needs a decision before the first member's device is tagged.
