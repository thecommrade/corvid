## Main-session notes

- ADR-0001: fair share only as scheduling when contended; **no quotas, no per-member limits** — any queue design here must not reintroduce them.
- Ports per ADR-0003: coordinator API 8091, status 8092 on the hub, tailnet-bound; Postgres as a **separate compose project** from the media stack.

## Recommendations for the spec

1. Postgres compose project: its own directory with top-level `name: corvid-db` (no `version:`), image pinned to a full tag (`postgres:18.6-trixie`, or `18.6-alpine` if size matters), bind mount `/srv/corvid/pg:/var/lib/postgresql` (18+ location; NOT /var/lib/postgresql/data), `shm_size: 256mb`, `restart: unless-stopped`, POSTGRES_PASSWORD via env file kept out of git. Cite R06-F6, F7, F8, F10.
2. Resource caps for the DB container: use `deploy.resources.limits: {cpus: '1.0', memory: 1g, pids: 200}` plus `deploy.resources.reservations.memory` — verified to be honored by docker compose v5.5.0 (R06-F2); never set deploy `reservations.cpus` (swarm-only). Keep `mem_limit`/`cpus` out to avoid the must-be-consistent rule (R06-F3). Tune the cap after measuring; a GTX-970-era hub should protect llama-server's RAM.
3. Healthcheck: `test: ["CMD-SHELL", "pg_isready -U $POSTGRES_USER -d $POSTGRES_DB"]`, interval 10s, timeout 5s, retries 5, start_period 30s; coordinator uses `depends_on: db: {condition: service_healthy}` if in the same project, or its own readiness loop if in a separate project. Pass real -U/-d so health probes don't spam failed-auth log lines (R06-F4, F12).
4. Schema migrations as /docker-entrypoint-initdb.d/*.sql only for the very first boot; everything after via `db/` migrations applied by the coordinator (initdb.d never re-runs and a failed script leaves a half-initialized dir) (R06-F9).
5. Network exposure: do NOT publish 5432 at all if the coordinator shares the Docker network; if it must be published, bind to the hub's tailnet IP only (`100.x.y.z:5432:5432`), never 0.0.0.0 — matches CLAUDE.md §5.6.
6. Queue claim query (one statement, no advisory locks): `UPDATE job SET state='running', claimed_by=$node, claimed_at=clock_timestamp(), lease_until=clock_timestamp()+interval '2 minutes' WHERE id = (SELECT id FROM job WHERE state='queued' AND (run_after IS NULL OR run_after<=now()) ORDER BY priority DESC, created_at FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *;` with partial index `CREATE INDEX job_queued_idx ON job (priority DESC, created_at) WHERE state='queued';` (R06-F15, F16, F20). Avoid OFFSET in claim queries (F16).
7. Wake-up without busy-polling: statement trigger `AFTER INSERT ON job … NOTIFY job_queued` with empty/key-only payload; workers LISTEN and also poll every ~5 s as a backstop (payload <8000 B, delivered only on commit) (R06-F18).
8. Lease/heartbeat for running jobs: `lease_until timestamptz` renewed by the executing agent; a reaper loop re-queues rows whose lease expired (`state='running' AND lease_until < now()`), bumping `attempt`. Use clock_timestamp() or client-side timestamps inside long transactions since now() is frozen at transaction start (R06-F22).
9. Roster schema: `node(node_id text PK, owner_login text, os text, arch text, caps jsonb, last_seen timestamptz, agent_version text, …)` written via `INSERT … ON CONFLICT (node_id) DO UPDATE SET last_seen=EXCLUDED.last_seen, caps=EXCLUDED.caps` (R06-F21); heartbeat every 10 s, node considered 'unreachable' after 40 s without a heartbeat, derived at read time (`CASE WHEN last_seen > now()-interval '40 seconds'`), never stored — mirrors Kubernetes Lease defaults (R06-F24, F25). Keep a separate append-only `heartbeat_log`/`job_run` table for the thank-you board, not the live row.
10. All time columns `timestamptz`, never bare `timestamp` (R06-F23).
11. Fair share with no quotas: at claim time pick the next job from the member with the fewest currently-running jobs (tie → oldest), i.e. per-member round-robin = max-min fairness; one member alone gets the whole pool, and a flood from one member cannot starve others (R06-F26, F28, F29). Put the same rule in front of llama-server (per-member FIFO lanes, round-robin dispatch into `--parallel` slots). Inside a host, express the co-op's share as weights (`cpu_shares`/cgroup cpu.weight) and reserve hard limits (`cpus`/cpu.max, `mem_limit`) for the OWNER's politeness caps (R06-F14, F27) — weights share, limits cap.
12. Identity for the API on the hub: coordinator listens on 127.0.0.1 only; expose it with `tailscale serve --bg <port>`; trust `Tailscale-User-Login` as the caller identity (Serve strips spoofed copies; only tailnet traffic gets headers); reject requests without the header (R06-F30). Do not rely on whois-by-source-IP on solarplexus: userspace netstack hands the backend a loopback connection (R06-F35). Keep `tailscale whois` / LocalAPI `/localapi/v0/whois` for kernel-mode nodes and for the agent's own CLI (R06-F31–F33).
13. Member devices must NOT be tagged (tags suppress identity headers); agents authenticate as the owner's login via the same headers, plus a `node_id` they generate locally (R06-F30).
14. Log policy: set `log_statement=none`, `log_min_duration_statement=-1`, `log_connections=''`, `log_disconnections=off` explicitly in the compose `command:` so defaults can't drift (R06-F37). Store only metadata in Postgres (who, which node, model name, token counts, durations, exit status); never prompt/completion text or job stdout. llama-server: `--no-slots`, never `--log-prompts-dir`, `--metrics` allowed (aggregate) (R06-F38). Write this as the docs/ 'what we log' page members read.
15. Credit rows to add to CLAUDE.md §4 in the same commit as the code: PostgreSQL (PostgreSQL License), postgres Docker Official Image (MIT Dockerfiles), Docker Compose (Apache-2.0), psycopg 3 (LGPL-3.0 — dynamic import from Python is fine), and note Tailscale Serve/whois usage under the existing Tailscale row; idea-credits for Hadoop Fair Scheduler, DRF, and Kubernetes leases.
16. Pin Postgres 18 (supported to 2030-11) unless the hub's Docker/kernel is old; plan `pg_upgrade --link` using the new /var/lib/postgresql layout (R06-F7, F11).

## Open questions

- Does `tailscale serve` (with identity headers) work on solarplexus while tailscaled runs in --tun=userspace-networking? Implied by the container image defaults (R06-F36) but unverified on bare metal — needs a 10-minute spike before the API design is frozen.
- Same compose project or two? Putting coordinator + Postgres in one project gives `depends_on: service_healthy` for free; separate projects (as asked) need a named external network or a tailnet-bound port. Decide in the coordinator ADR.
- Postgres major: 18 vs 17 on the hub — does the hub's Docker version/kernel support the 18 image cleanly, and who owns the bind-mount dir (uid 999 vs arbitrary --user)?
- Agent identity: member-login headers (no tags) vs tagged machines with a shared secret — tags remove identity headers (R06-F30); what should the roster key on when one member owns several machines (node_id + owner_login?).
- Fair-share granularity for inference: per request at the coordinator vs per token inside llama-server slots; does llama-server's own slot queue already behave acceptably at 6 users (measure before building).
- Retention for the metadata-only logs: how long do job_run / heartbeat_log rows live, and is the contribution board fed from them or from a rollup table?
- Do we want LISTEN/NOTIFY at all in v1, or is 5-second polling by ≤20 agents simply fine? (Probably fine; NOTIFY is an optimization.)
- Ready-made Python queue libs on SKIP LOCKED exist; hand-rolled is ~30 lines. Confirm §7 non-goal reading: hand-roll here is acceptable because no scheduler is being invented.
- Where does `tailscale whois` matter then? Kernel-mode nodes (laptops) can use source-IP whois for their local agent UI; confirm whether any API is served from a kernel-mode node or everything fronts through the hub.

**Completeness critic — missing for a plan writer:**

- Reuse-vs-new vs Immich's Postgres (spec §6.1 R06 asked for the decision to be recorded): no fact on what image/version Immich's `immich-db` container pins (the vectorchord/pgvecto.rs-patched Postgres) or whether Immich's docs permit sharing its DB with other apps; record 'new, separate project' (or not) with the citation.
- Hub placement facts absent: which disk/filesystem holds PGDATA on solarplexus (/ with 242 GB free vs /mnt/disk1\|disk2 vs the mergerfs/FUSE pool — is a FUSE pool acceptable for a Postgres data dir?), the host path convention for the new compose project (where the media stack's compose files live, owner), bind-mount ownership (image default uid 999 vs `--user <unattended-uid>` per F13 so inspection/backups need no root), and a backup method/destination (pg_dump via `docker compose exec`, schedule, executor) — 'data dir disk' was a key question and backups are unaddressed.
- Rights of the unattended user on solarplexus: is it in the `docker` group (root-equivalent — acceptable to the founder?), or is every `docker compose` step `executor: Opus (splx-root)`? Rootless Docker considered? This sets executor tags for the whole Phase 2 plan and is not in the facts.
- Compose version actually installed on the hub: Docker is the Ubuntu `docker.io` package (29.1.3-0ubuntu3~24.04.2, R00-F9) and the compose plugin ships separately (`docker-compose-v2`). F2 verifies deploy.resources handling against docker/compose v5.5.0 source, not the hub's version; do F2, F4 `start_interval` (needs Engine ≥25 + recent compose) and F5 `bind.create_host_path` hold at `docker compose version` on solarplexus, or is upgrading compose a plan step?
- Postgres port/publish decision and syntax: should Postgres be published at all (API in the same compose network → no `ports:`), or on `127.0.0.1:5432` / `<tailnet-ip>:5432` for Grafana (R07)/psql? Missing: compose `ports:` host-IP syntax (`[HOST_IP:]HOST_PORT:CONTAINER_PORT`, long-form `host_ip:`) that the bind-target CI lint requires, and the constraint that binding a published port to the tailnet IP requires kernel-mode tailscaled (no interface IP in userspace mode).
- Where the coordinator API runs — container in the same compose project vs host systemd unit (user unit needs linger per R00-F8; no uv on the hub) — is undecided and unsupported by facts for either path. Container path needs: bind-mount of the hub's socket (`/run/tailscale/tailscaled.sock` per the R00 log, not F34's `/var/run/tailscale`), the `tailscale` CLI in the image or the raw LocalAPI HTTP contract (required Host header / `Sec-Tailscale` / 403 rules), how the API sees the peer's tailnet IP (`network_mode: host` vs bridge + published port), and whether solarplexus's policy rule `100 from <docker-net> → <vpn-table>` (R00-F3) pulls replies from a NEW compose bridge network into the VPN table and breaks tailnet→container traffic.
- Identity conflict with ADR-0002: F30 says Serve identity headers are not populated for tagged devices, and whois on a tagged node returns no real user (the `tagged-devices` pseudo-user) — but ADR-0002 tags contributing member machines `tag:member`, so a member browsing from their own contributing laptop has no zero-login identity. Needs the fact (what `WhoIsResponse.UserProfile`/`Node.User` holds for a tagged node) and a resolution: untag member devices (ACL by user/group), per-member tags, or a coordinator-maintained node→owner table.
- Identity mechanism for the API given ADR-0003's Caddy front door: Serve proxies only to localhost (F30) and listens on `<tailnet-ip>:443`/`:80` — the ports ADR-0003 gives Caddy. Does `tailscale serve --https=443` conflict with Caddy bound to the tailnet IP :443 in kernel mode? Is the chain Serve→Caddy(127.0.0.1)→apps (headers forwarded by Caddy) or Caddy→API with whois on `X-Forwarded-For` (trusted_proxies)? For the headers path: version pin (do `--http=<port>` and `Tailscale-User-*` exist in 1.98.4 vs 1.102.3 — spec demands 'with version pinned'), does `--http` work without HTTPS certs enabled on the tailnet (R00-D11 UNVERIFIED → S-05, still blocked), does `serve --bg` persist across tailscaled restarts/reboots, and who runs it (root/operator → `Opus (splx-root)`). Also state that Phase 2 assumes the kernel-mode hub (Phase 0 step 2) and what then holds for whois on direct connections (F35/F36 only cover userspace mode).
- Which Tailscale node identifier is the roster primary key: `tailcfg.Node.StableID` (stable across re-auth/rename) vs `ID` vs `Name` (changes on rename) vs node key (rotates on re-auth/180-day expiry per ADR-0002)? F31/F32 list the fields but not their stability; a wrong pick duplicates nodes after a member re-authenticates.
- Heartbeat interval and node-down threshold are not chosen: F24/F25 give Kubernetes' 10 s lease / 40 s timeout (4×), but Phase 2 acceptance needs 'N = 3 × the heartbeat interval chosen in R06'. State the recommended interval, the down threshold, the down-detection query (server-side `last_seen < now() - interval`, per F22), and the agent's retry/backoff on failure.
- Roster/heartbeat schema is not proposed: latest-only upsert (F21) vs an append-only heartbeat/session history for the thank-you board (CLAUDE.md §3.4; ADR-0001 'contributions appear only as thanks') and, if history, its retention; representation of the opt-in capability report (`offers: none` default; JSONB vs columns); which fields the agent may report (caps, GPU, idle/battery state) — no fact supports these choices.
- Queue mechanics beyond the lock clause (key question asked for the pattern): the canonical claim statement (`UPDATE jobs … WHERE id = (SELECT id … ORDER BY … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *`), that the row lock lasts only for the transaction (long-running jobs need a `running` state + lease/heartbeat + reclaim rule when a node dies), psycopg3 transaction/autocommit semantics for holding vs releasing the lock, and LISTEN/NOTIFY consumption from psycopg3 (dedicated connection outside the pool).
- Fair share is background only (F26–F29): no implementable rule for a friends-scale SQL queue (e.g. dequeue ordered by per-member running-job count then age = max-min in one query, no quota table), and nothing on inference-side contention — llama-server `--parallel`/`-np` slots, continuous batching, and what happens when all slots are busy (FIFO queue vs 503) — which is the only 'fair share' Phases 1–2 actually exercise. Also whether `/slots` (F38, enabled by default) exposes prompt text and should be disabled under the log policy.
- Log-policy gaps: Postgres `log_min_error_statement` defaults to `error`, so a failing INSERT/UPDATE is logged with its full SQL text (literal values included) despite F37's `log_parameter_max_length_on_error=0` — needs a setting or parameters-only discipline; uvicorn/FastAPI access-log defaults (method+path+query string; `--no-access-log`); Docker `json-file` driver has no rotation by default (`logging.options.max-size/max-file`); retention window for metadata logs/heartbeat history; whether `Tailscale-User-Login` (an email) may be stored/logged (spec §3.8 forbids usernames in the repo; DB/log policy unstated).
- Healthcheck false positive: pg_isready (F12) returns 0 during first-run initdb/init-script phase because the entrypoint's temporary server listens on the unix socket only, so `depends_on: condition: service_healthy` (F4) fires early and the dependent's first connection is reset when the temp server stops; usual fix is `pg_isready -h 127.0.0.1 -U … -d …` (TCP only with the real server) with `$$` env escaping in compose — not captured.
- Concrete resource caps for hub services are not recommended: the Phase 2 spec must set `cpus:`/`mem_limit:`/`shm_size` for Postgres and the API on a 4-thread/16 GB hub also running Plex/Immich/Tdarr; F8/F14 give mechanics but no values, nothing on Postgres's 128 MB default `shared_buffers`/OOM behaviour under a small `mem_limit`, and no restart-policy recommendation (`unless-stopped`).
- Secrets and migrations: where `POSTGRES_PASSWORD` lives (`.env` git-ignored; `POSTGRES_PASSWORD_FILE` supported by the image — not in F7) and how schema changes are applied after first init, since `/docker-entrypoint-initdb.d` never re-runs (F9): `db/` migrations via `psql -f` through `docker compose exec`, a Python migrator, or a tool (needing its own §4 row).
- Credit rows incomplete for `add-dependency`: F39–F44 give licenses but no authors (docker-library/postgres maintainers; Docker Inc. for Compose; Daniele Varrazzo/Psycopg Team; Sebastián Ramírez for FastAPI; Encode/Tom Christie for uvicorn) and no pinned image tag decision (17.x vs 18.x given F7's volume-path change; trixie vs alpine) — the §4 row needs all four columns at the pinned version.
