## Main-session notes

- ADR-0001: fair share only as scheduling when contended; **no quotas, no per-member limits** — the Phase 2 claim query orders by the member with the fewest running jobs and never refuses.
- Ports per ADR-0003 (amended): coordinator API 8091 and status 8092 bind loopback on the hub behind Caddy; Postgres as a **separate compose project** from the media stack with no published port.

## Recommendations for the spec

1. Postgres compose project: its own directory with top-level `name: corvid-db` (no `version:`), image pinned to a full tag (`postgres:18.6-trixie`, or `18.6-alpine` if size matters), bind mount `/srv/corvid/pg:/var/lib/postgresql` (18+ location; NOT /var/lib/postgresql/data), `shm_size: 256mb`, `restart: unless-stopped`, POSTGRES_PASSWORD via env file kept out of git. Cite R06-F6, F7, F8, F10.
2. Resource caps for the DB container: use `deploy.resources.limits: {cpus: '1.0', memory: 1g, pids: 200}` plus `deploy.resources.reservations.memory` — verified to be honored by docker compose v5.5.0 (R06-F2); never set deploy `reservations.cpus` (swarm-only). Keep `mem_limit`/`cpus` out to avoid the must-be-consistent rule (R06-F3). Tune the cap after measuring; a GTX-970-era hub should protect llama-server's RAM.
3. Healthcheck: `test: ["CMD-SHELL", "pg_isready -U $POSTGRES_USER -d $POSTGRES_DB"]`, interval 10s, timeout 5s, retries 5, start_period 30s; coordinator uses `depends_on: db: {condition: service_healthy}` if in the same project, or its own readiness loop if in a separate project. Pass real -U/-d so health probes don't spam failed-auth log lines (R06-F4, F12).
4. Schema migrations as /docker-entrypoint-initdb.d/*.sql only for the very first boot; everything after via `db/` migrations applied by the coordinator (initdb.d never re-runs and a failed script leaves a half-initialized dir) (R06-F9).
5. Network exposure: do NOT publish 5432 at all if the coordinator shares the Docker network; if it must be published, bind to the hub's tailnet IP only (`100.x.y.z:5432:5432`), never 0.0.0.0 — matches CLAUDE.md §5.6.
6. Queue claim query (one statement, no advisory locks): `UPDATE job SET state='running', claimed_by=$node, claimed_at=clock_timestamp(), lease_until=clock_timestamp()+interval '2 minutes' WHERE id = (SELECT id FROM job WHERE state='queued' AND (run_after IS NULL OR run_after<=now()) ORDER BY priority DESC, created_at FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *;` with partial index `CREATE INDEX job_queued_idx ON job (priority DESC, created_at) WHERE state='queued';` (R06-F15, F16, F20). Avoid OFFSET in claim queries (F16).
7. Wake-up without busy-polling: statement trigger `AFTER INSERT ON job … NOTIFY job_queued` with empty/key-only payload; workers LISTEN and also poll every ~5 s as a backstop (payload <8000 B, delivered only on commit) (R06-F18).
8. Lease/heartbeat for running jobs: `lease_until timestamptz` renewed by the executing agent; a reaper loop re-queues rows whose lease expired (`state='running' AND lease_until < now()`), bumping `attempt`. Use clock_timestamp() or client-side timestamps inside long transactions since now() is frozen at transaction start (R06-F22).
9. Roster schema: `node(node_id text PK, owner_login text, os text, arch text, caps jsonb, last_seen timestamptz, agent_version text, …)` written via `INSERT … ON CONFLICT (node_id) DO UPDATE SET last_seen=EXCLUDED.last_seen, caps=EXCLUDED.caps` (R06-F21); heartbeat every 10 s, node considered 'unreachable' after 40 s without a heartbeat, derived at read time (`CASE WHEN last_seen > now()-interval '40 seconds'`), never stored — mirrors Kubernetes Lease defaults (R06-F24, F25). Keep a separate append-only `heartbeat_log`/`job_run` table for the thank-you board, not the live row.
10. All time columns `timestamptz`, never bare `timestamp` (R06-F23).
11. Fair share with no quotas: at claim time pick the next job from the member with the fewest currently-running jobs (tie → oldest), i.e. per-member round-robin = max-min fairness; one member alone gets the whole pool, and a flood from one member cannot starve others (R06-F26, F28, F29). Put the same rule in front of llama-server (per-member FIFO lanes, round-robin dispatch into `--parallel` slots). Inside a host, express the co-op's share as weights (`cpu_shares`/cgroup cpu.weight) and reserve hard limits (`cpus`/cpu.max, `mem_limit`) for the OWNER's politeness caps (R06-F14, F27) — weights share, limits cap.
12. Identity for the API on the hub: coordinator listens on 127.0.0.1 only; expose it with `tailscale serve --bg <port>`; trust `Tailscale-User-Login` as the caller identity (Serve strips spoofed copies; only tailnet traffic gets headers); reject requests without the header (R06-F30). Do not rely on whois-by-source-IP on solarplexus: userspace netstack hands the backend a loopback connection (R06-F35). Keep `tailscale whois` / LocalAPI `/localapi/v0/whois` for kernel-mode nodes and for the agent's own CLI (R06-F31–F33).
13. Member devices must NOT be tagged (tags suppress identity headers); agents authenticate as the owner's login via the same headers, plus a `node_id` they generate locally (R06-F30).
14. Log policy: set `log_statement=none`, `log_min_duration_statement=-1`, `log_connections=''`, `log_disconnections=off` explicitly in the compose `command:` so defaults can't drift (R06-F37). Store only metadata in Postgres (who, which node, model name, token counts, durations, exit status); never prompt/completion text or job stdout. llama-server: `--no-slots`, never `--log-prompts-dir`, `--metrics` allowed (aggregate) (R06-F38). Write this as the docs/ 'what we log' page members read.
15. Credit rows to add to CLAUDE.md §4 in the same commit as the code: PostgreSQL (PostgreSQL License), postgres Docker Official Image (MIT Dockerfiles), Docker Compose (Apache-2.0), psycopg 3 (LGPL-3.0 — dynamic import from Python is fine), and note Tailscale Serve/whois usage under the existing Tailscale row; idea-credits for Hadoop Fair Scheduler, DRF, and Kubernetes leases.
16. Pin Postgres 18 (supported to 2030-11) unless the hub's Docker/kernel is old; plan `pg_upgrade --link` using the new /var/lib/postgresql layout (R06-F7, F11).

## Open questions

- Does `tailscale serve` (with identity headers) work on solarplexus while tailscaled runs in --tun=userspace-networking? Implied by the container image defaults (R06-F36) but unverified on bare metal — needs a 10-minute spike before the API design is frozen.
- Same compose project or two? Putting coordinator + Postgres in one project gives `depends_on: service_healthy` for free; separate projects (as asked) need a named external network or a tailnet-bound port. Decide in the coordinator ADR.
- Postgres major: 18 vs 17 on the hub — does the hub's Docker version/kernel support the 18 image cleanly, and who owns the bind-mount dir (uid 999 vs arbitrary --user)?
- Agent identity: member-login headers (no tags) vs tagged machines with a shared secret — tags remove identity headers (R06-F30); what should the roster key on when one member owns several machines (node_id + owner_login?).
- Fair-share granularity for inference: per request at the coordinator vs per token inside llama-server slots; does llama-server's own slot queue already behave acceptably at 6 users (measure before building).
- Retention for the metadata-only logs: how long do job_run / heartbeat_log rows live, and is the contribution board fed from them or from a rollup table?
- Do we want LISTEN/NOTIFY at all in v1, or is 5-second polling by ≤20 agents simply fine? (Probably fine; NOTIFY is an optimization.)
- Ready-made Python queue libs on SKIP LOCKED exist; hand-rolled is ~30 lines. Confirm §7 non-goal reading: hand-roll here is acceptable because no scheduler is being invented.
- Where does `tailscale whois` matter then? Kernel-mode nodes (laptops) can use source-IP whois for their local agent UI; confirm whether any API is served from a kernel-mode node or everything fronts through the hub.
