## Purpose

Facts a plan can cite for: chat front-end for phase 1. Agent summary (verbatim, may contain its own working notes):

> R08 — Chat front-end for Phase 1 (verified 2026-08-22, primary sources only) SUMMARY VERDICT - Phase 1 demo ("a friend gets a completion from a model spread across two houses"): llama-server's built-in Web UI is sufficient and costs zero extra services. It is MIT, ships inside the llama-server binary, stores each person's conversations in their own browser (IndexedDB), and has no login at all. It is single-user-by-design: no server-side per-user history, no identity. Bind llama-server to the tailnet interface (its default is 127.0.0.1:8080) and friends open http://solarplexus:8080. - First member-facing chat (Phase 2 "bookmark the site"): Open WebUI v0.11.0 is the only candidate that satisfies all four asks at once — (a) zero-login via trusted headers (WEBUI_AUTH_TRUSTED_EMAIL_HEADER / _NAME_HEADER), with an official Tailscale Serve tutorial (Serve injects Tailscale-User-Login / Tailscale-User-Name); (b) per-user chat history (SQLite, one container, default DATABASE_URL=sqlite:///{DATA_DIR}/webui.db); (c) telemetry already off in the official image (SCARF_NO_ANALYTICS=true, DO_NOT_TRACK=true, ANONYMIZED_TELEMETRY=false; ENABLE_OTEL default False) with ENABLE_VERSION_UPDATE_CHECK / ENABLE_COMMUNITY_SHARING / OFFLINE_MODE knobs; (d) single compose service. Licence caveat: since ~v0.6 it is NOT MIT — it is the "Open WebUI License", BSD-3-Clause plus a clause-4 branding restriction that is waived for deployments with ≤50 end users in any rolling 30-day period (CORVID qualifies; we would not rebrand anyway). Privacy caveat: ENABLE_ADMIN_CHAT_ACCESS defaults True (admins can read every user's chats) — set False or disclose per §5.7. - LibreChat v0.8.7 (MIT): no trusted-header auth exists in a release — the feature is an open, unmerged PR (#8562, opened 2025-07-20; issue #1856 still open). Its compose needs MongoDB (+ rag_api by depends_on) — not a single service. OIDC is supported, so a future zero-login path is Tailscale's tsidp (experimental). Defer. - Lobe Chat (repo now lobehub/lobehub, v2.2.14): "LobeHub Community License" (Apache 2.0 + extra conditions: derivative works need a commercial licence; producer may tighten terms). Auth is Better Auth (email/password, OAuth/OIDC providers), sessions in the DB; no trusted-header mode documented; minimum three services (app + PostgreSQL/pgvector + S3/RustFS). Not a fit. - Hollama 0.35.4 (MIT): runs entirely in the browser, no accounts, history per browser, one container (ghcr.io/fmaclen/hollama, port 4173), supports OpenAI-compatible servers, no analytics packages declared. A fine zero-backend alternative to the llama.cpp UI, but "per-user history" is just "per-browser". - Also checked: AnythingLLM (MIT; multi-user Docker-only; telemetry ON by default, DISABLE_TELEMETRY=true to stop), Hugging Face chat-ui (Apache-2.0; MongoDB-backed, OPENAI_BASE_URL only). Neither documents header auth; neither beats Open WebUI for this use. ZERO-LOGIN MECHANISM (verified): Tailscale Serve proxies to a local port and adds Tailscale-User-Login, Tailscale-User-Name, Tailscale-User-Profile-Pic; it strips those headers from incoming requests (anti-spoofing); headers are absent for Funnel traffic and for tagged devices; the backend must be reachable only via Serve (listen on localhost / publish the container port on 127.0.0.1). Tailscale Serve requires HTTPS certificates enabled on the tailnet. Alternative identity sources: `tailscale whois --json <ip>` (CLI) and tsidp (experimental OIDC IdP, BSD-3, ghcr.io/tailscale/tsidp). RISK FLAGGED FOR THE HUB: solarplexus runs tailscaled with --tun=userspace-networking. Tailscale's userspace-networking and Serve docs do not state whether Serve works in that mode (neither yes nor no). This must be spiked before the Open WebUI + Serve design is committed; the Open WebUI tutorial's tailscale-sidecar compose pattern is the documented fallback.

## Main-session notes

- Decided in the Phase 1 spec: Phase 1 ships llama-server's built-in web UI (MIT) at `/chat` → `:8090`; Open WebUI (Open WebUI License = BSD-3 + branding clause; trusted-header auth via `X-Corvid-User`) is the Phase 2 stretch task with its own ADR; `:8093` reserved.

## Recommendations for the spec

1. Phase 1 exit demo: use llama-server's built-in Web UI (MIT, inside the binary) — no extra service. Start llama-server with --host <solarplexus tailnet IP> (default is 127.0.0.1) and --rpc <workers>; friends open http://solarplexus:8080. Accept that history is per-browser and there is no identity; do not set --api-key for the demo (the UI is open to the tailnet, which is the security boundary per CLAUDE.md §3.2).
2. Member-facing chat (Phase 2 'bookmark the site'): adopt Open WebUI, pinned to a vX.Y.Z tag (v0.11.0 today; verify the GHCR tag exists — R08-F12), one container, SQLite on the open-webui volume, published on 127.0.0.1:8080 only, fronted by `tailscale serve` on solarplexus. Env: WEBUI_AUTH_TRUSTED_EMAIL_HEADER=Tailscale-User-Login, WEBUI_AUTH_TRUSTED_NAME_HEADER=Tailscale-User-Name, DEFAULT_USER_ROLE=user (else friends land 'pending'), OPENAI_API_BASE_URL=http://<llama-server>:8080/v1 with a dummy OPENAI_API_KEY, ENABLE_OLLAMA_API=false, ENABLE_COMMUNITY_SHARING=false, ENABLE_VERSION_UPDATE_CHECK=false (or OFFLINE_MODE=true if RAG downloads are not wanted), ENABLE_ADMIN_CHAT_ACCESS=false and ENABLE_ADMIN_EXPORT=false (or disclose per §5.7 that the admin can read chats).
3. Record Open WebUI in CLAUDE.md §4 as 'Open WebUI License (BSD-3-Clause + branding clause)', not MIT; note CORVID's ≤50-end-users exemption (clause 4(i)) and the house rule: never rebrand it. Write ADR 'chat front-end' capturing this choice and the rejected options (LibreChat: no header auth in any release, MongoDB+rag_api; Lobe: custom licence + 3-service minimum + no header auth).
4. Before committing to the Serve design, run a spike on solarplexus: does `tailscale serve` work under --tun=userspace-networking and do the Tailscale-User-* headers arrive at a local listener (curl a tiny echo server)? If not, use the Open WebUI tutorial's tailscale-sidecar compose pattern (tailscale/tailscale container + serve.json -> http://open-webui:8080) or a tiny Python proxy that calls `tailscale whois --json` and injects the header itself.
5. Header-spoofing guard as a CI/ops check (ties to §5.6): the Open WebUI container must never be published on 0.0.0.0; only the Serve path may reach it. Tailscale Serve strips incoming Tailscale-User-* headers, but only if every request really goes through Serve.
6. Shared/tagged-device caveat: identity headers are not populated for tagged devices; design member nodes as user-owned (untagged) devices, and test what header value a member who logged into Tailscale with GitHub (non-email login) produces before relying on it as an 'email'.
7. Keep Hollama (MIT, one container, browser-local data) as the documented zero-backend fallback if Open WebUI ever feels heavy; keep LibreChat on the watch list keyed to PR #8562 merging or tsidp leaving 'experimental' (OIDC path). Do not adopt Lobe Chat.
8. Telemetry statement for members: Open WebUI's official image already ships SCARF_NO_ANALYTICS=true, DO_NOT_TRACK=true, ANONYMIZED_TELEMETRY=false, ENABLE_OTEL off; what remains outbound is the version check (disable) and any HF model downloads for RAG/STT (document or set OFFLINE_MODE).

**Completeness critic — missing for a plan writer:**

- Open WebUI — trusted-header auto-registration × DEFAULT_USER_ROLE: F4 says trusted headers do 'automatic registration and login' and F7 says DEFAULT_USER_ROLE defaults to `pending`, but the dossier never states what role a friend gets on first visit via Tailscale headers. (auths.py at v0.11.0: the trusted-header path calls signup_handler(), first user → admin, every later user → Config 'ui.default_user_role' = pending.) The plan needs an explicit fact: with defaults, friends 2..N land as 'pending' and cannot chat until the founder approves them — so the compose must set DEFAULT_USER_ROLE=user (Tailscale sends no role header). Also state whether ENABLE_SIGNUP / ENABLE_LOGIN_FORM gate trusted-header auto-registration (the 403 checks live in the signup endpoint, not signup_handler — confirm).
- Open WebUI — PersistentConfig/ConfigVar semantics are absent: env vars such as OPENAI_API_BASE_URL, OPENAI_API_KEY(S), DEFAULT_USER_ROLE, ENABLE_SIGNUP, ENABLE_LOGIN_FORM, ENABLE_OLLAMA_API are 'ConfigVar' — read from env on FIRST boot, then stored in the SQLite DB and ignored on later restarts unless ENABLE_PERSISTENT_CONFIG=false. A plan writer who edits the compose later will be silently ignored. Need: which of the cited vars are ConfigVar, and the recommended setting of ENABLE_PERSISTENT_CONFIG for a compose-managed deploy.
- Open WebUI → llama-server wiring: what exact env makes Open WebUI talk to llama-server — OPENAI_API_BASE_URL=http://<host>:8080/v1 plus OPENAI_API_KEY=? (config.py default is ''): does Open WebUI accept an EMPTY key against a keyless llama-server, or must a dummy/real --api-key be set on both sides? Also: ENABLE_OLLAMA_API=True by default (F9) with OLLAMA_BASE_URL defaulting to localhost:11434 — confirm it should be set false to stop polling a non-existent Ollama, and whether OPENAI_API_BASE_URL='' really falls back to api.openai.com (F9) — i.e. a misconfigured hub would send prompts to OpenAI.
- Open WebUI — outbound calls beyond telemetry are incomplete: config.py sets RAG_EMBEDDING_MODEL='sentence-transformers/all-MiniLM-L6-v2' with RAG_EMBEDDING_MODEL_AUTO_UPDATE = not OFFLINE_MODE, i.e. a Hugging Face download at first start unless OFFLINE_MODE=true. - Open WebUI — hub footprint not recorded: image size of ghcr.io/open-webui/open-webui:v0.11.0 (the :main image is multi-GB because it bundles sentence-transformers/torch), idle RAM and CPU on start, and whether the slim/cuda variants exist. solarplexus specs are UNKNOWN and it also hosts llama-server; the plan needs numbers.

Need a definite fact: can v0.11.0 be served under https://hub/chat, or must it get its own Serve port (--https=8443 etc.) or its own sidecar hostname? Which HTTPS ports does Serve allow (443/8443/10000 only, or any)?
- Tailscale Serve on the hub (F34): left 'must be spiked' but is largely answerable from docs — the tailscale/tailscale container documents TS_USERSPACE as 'Enabled by default' and Open WebUI's own tutorial (F5) runs `serve` inside that container, so Serve demonstrably works in userspace mode; what remains is whether the host tailscaled with --tun=userspace-networking behaves the same. Also unanswered: are identity headers injected for `tailscale serve --http=80` (plain HTTP) or only HTTPS, and is HTTPS-certs/MagicDNS currently enabled on the CORVID tailnet (Phase 0 found MagicDNS off on the laptop) — a precondition stated in F31.
