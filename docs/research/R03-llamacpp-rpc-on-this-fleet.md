Release/version landscape. llama.cpp now has two tag lines: vX.Y.Z "stable" tags (v0.2.0 published 2026-08-21, commit bb4caa75 = nightly b10566; its only asset is nightly-tag.txt containing "b10566", binaries live on the b10566 release) and b[NUM] nightly prereleases on almost every master commit (b10581 at 10:13Z today, 26 assets). Binaries. The Linux release tarballs (ubuntu-x64, ubuntu-vulkan-x64, also macos-arm64 and win-cpu/win-cuda zips) DO ship ggml-rpc-server (the tool was renamed from rpc-server; the executable is ggml-rpc-server / ggml-rpc-server.exe) plus libggml-rpc, because release.yml sets CMAKE_ARGS "-DGGML_RPC=ON" for all jobs and tars the whole build/bin. But there is NO Linux CUDA release asset at all: Linux assets are CPU (GGML_BACKEND_DL with ~15 CPU variant .so files), Vulkan, SYCL, OpenVINO. Linux + CUDA + RPC therefore means building from source (or an in-house container). The official Docker images are CUDA 12.8.1 (tags *-cuda) and 13.3.0 (*-cuda13), built WITHOUT GGML_RPC (cuda.Dockerfile's cmake line has no -DGGML_RPC=ON; GGML_RPC defaults OFF) and light/server targets copy only llama/llama-cli/llama-completion or llama/llama-server — so no official image provides ggml-rpc-server, and llama-server inside them cannot use --rpc ("failed to find RPC backend"). 3. Building. tools/rpc/README.md (the only RPC build doc — docs/build.md has no RPC section): cmake -DGGML_CUDA=ON -DGGML_RPC=ON on each worker; the main host must ALSO be built with -DGGML_RPC=ON plus its own local backends. docs/build.md: cmake -B build -DGGML_CUDA=ON builds for the attached GPU (GGML_NATIVE -> CMAKE_CUDA_ARCHITECTURES=native when CUDA>=11.6 and CMake>=3.24); -DGGML_NATIVE=OFF for a cover-all build; -DCMAKE_CUDA_ARCHITECTURES="86;89" to pin; -DCMAKE_CUDA_COMPILER=/opt/cuda-X/bin/nvcc (+rpath) to pick a toolkit. ggml-cuda CMake needs CMake>=3.18 and fails hard if no CUDA toolkit. No explicit minimum toolkit version is enforced; code has CUDART_VERSION>=11070/11080/12000 feature gates. 4. GTX 970 (Maxwell, cc 5.2) on driver 535 / CUDA 12.2. (a) llama.cpp's non-native default arch list includes 50-virtual (PTX only) ONLY when the toolkit is <13 (comment: "50 == Maxwell, lowest CUDA 12 standard"); CUDA 13 builds cannot target it at all. (b) NVIDIA: CUDA 12.x "will continue to support building applications for these architectures"; CUDA 13.0 "Offline compilation and library support for these architectures have been removed". (c) Driver math: CUDA 12.2 GA's bundled driver is 535.54.03; minor-version compatibility lets any 12.x toolkit run on >=525.60.13 (<580) EXCEPT "Applications that compile device code to PTX will not work on older drivers" and it "requires passing the target architecture argument to NVCC (-arch=sm_xx)". Consequence: on the hub, either build with the 12.2 toolkit that matches driver 535, or with any 12.x toolkit but pass -DCMAKE_CUDA_ARCHITECTURES=52-real (SASS, not PTX). Forward-compat packages are Data-Center/NGC-RTX/Jetson only, so CUDA 13 on a GTX 970 with driver 535 is not an option; CUDA 13.x needs driver >=580 (13.1 GA >=590.44.01). (d) Performance: Maxwell is below GGML_CUDA_CC_DP4A (610) so MMQ int8 kernels are unavailable and below PASCAL so mul_mat_vec fusion is disabled — it works via the slower generic/cuBLAS paths. Binding to anything but 127.0.0.1 prints the upstream banner "Never expose the RPC server to an open network! ## Main-session notes

- Install path for Phase 1 (from S-02): release tarball `llama-<tag>-bin-ubuntu-vulkan-x64.tar.gz` per node, pinned tag (b10581 verified), extracted under the service user; CUDA builds only if Vulkan throughput disappoints (then per-node CUDA 12.x on the hub, 13.x elsewhere — see R01-F27…F30).
- Worker VRAM cannot be capped server-side at b10581 (no `--mem`): bound it with model choice, `-ts`/`-ngl` on the host, and `-d Vulkan0` device selection; record this in the Phase 1 spec and ADR-0005 notes.
- Acceptance must check the `llama-bench`/`llama-server` backend string contains `RPC` and the worker log shows `Accepted client connection` — otherwise the run silently fell back to local.
- Worker processes as `systemd-run --user --unit=…` (transient service) or proper user units with linger (hub linger is off until Phase 0 step 2).

## Recommendations for the spec

1. Pin llama.cpp to a single tag for the whole fleet and record it in the spec as 'v0.2.0 (= b10566)'; RPC protocol 5.1.0 mismatch across builds is a hard failure, so every node's ggml-rpc-server and the hub's llama-server must come from the same tag (F1, F10).
2. Linux CUDA nodes must build from source: cmake -B build -DGGML_CUDA=ON -DGGML_RPC=ON (add -DGGML_NATIVE=OFF or an explicit CMAKE_CUDA_ARCHITECTURES when building on one box for another). Do not plan on the official Docker images or the ubuntu release tarballs for GPU RPC workers — the tarballs are CPU/Vulkan only and the images lack the RPC backend (F3, F4, F7). The CPU/Vulkan tarballs are still useful for a quick no-GPU smoke test (they do contain ggml-rpc-server).
3. Hub (GTX 970, driver 535): build with the CUDA 12.2 toolkit that matches driver 535, or with any 12.x toolkit plus -DCMAKE_CUDA_ARCHITECTURES=52-real so Maxwell gets SASS rather than PTX (F17, F21, F23, F24). Never install CUDA 13 on that box for this purpose (needs driver >=580 and cannot target cc 5.2). Treat the 970 as a 'fits, but slow' device (no MMQ/dp4a, F18) — primarily extra VRAM for the split, and consider the Vulkan backend as a fallback experiment if the CUDA 12.2 build fights the host toolchain.
4. RTX 3050 node on CUDA 13.1: default arch list covers 86-real; requires driver >=590.44.01 (F22). RTX 2070 Super (cc 7.5) is covered by every default list. Keep per-node builds native (GGML_NATIVE on) since each node compiles its own ggml-rpc-server.
5. Write the rpc-server unit as: ExecStart=.../ggml-rpc-server -H <node's Tailscale IPv4> -p 50052 [-c] [-d CUDA0]; -H must be a dotted IPv4 literal (F10) and the upstream 'not secure' banner will print and is expected (F9). Add the spec sentence that the RPC server is unauthenticated raw TCP and the tailnet is the only boundary; combine with Tailscale ACLs limiting port 50052 to the hub.
6. Resolve the hub's Tailscale userspace-mode problem before Phase 1 (F29, F30): either switch solarplexus to kernel/tun mode, or run llama-server on a tun-mode node and keep the hub as a worker only after confirming it can accept inbound tailnet TCP. This is an ADR-worthy decision (topology ADR 0006 is reserved).
7. llama-server on the hub: --host <tailnet IPv4> --port 8080 --rpc <worker1>:50052,<worker2>:50052 -ngl auto (default) and let the default free-memory split do the work; only add -ts if the split is bad. Use --list-devices first to confirm RPC<n>[host:port] devices appear (F11, F12). Keep logging at default -lv 3 and never use -v or --log-prompts-dir in service units (F14); consider --no-slots and leave --metrics/--props off unless needed; optionally --log-file to a member-readable location for the thank-you board.
8. Benchmark the split with llama-bench --rpc <servers> -ngl 99 before committing to a model, since RPC exists to fit, not to speed up (F15).
9. Service user: run ggml-rpc-server as a dedicated non-root user under a user manager with loginctl enable-linger and the unit in ~/.config/systemd/user (F27, F28); verify ls -l /dev/nvidia* shows 0666 (F25) and, if a distro has tightened it, add the user to the group named by the device GID rather than changing module parameters. Set LLAMA_CACHE (or let it default to ~/.cache/llama.cpp/rpc) to a disk with room for the cached tensors when using -c.
10. Credit rows: llama.cpp row already exists; add the release/tag convention and the RPC maintainer handle (rgerganov) to docs, and add Tailscale userspace-mode note to the hub's page.
