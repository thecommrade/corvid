Release/version landscape. llama.cpp now has two tag lines: vX.Y.Z "stable" tags (v0.2.0 published 2026-08-21, commit bb4caa75 = nightly b10566; its only asset is nightly-tag.txt containing "b10566", binaries live on the b10566 release) and b[NUM] nightly prereleases on almost every master commit (b10581 at 10:13Z today, 26 assets). Every file this dossier cites (tools/rpc/README.md, rpc-server.cpp, ggml-rpc.h, ggml-cuda CMakeLists, common/arg.cpp, server README, docker files, release.yml CMAKE_ARGS) is byte-identical between b10566 and b10581, so "pin v0.2.0 (=b10566)" is safe and everything below applies. 2. Binaries. The Linux release tarballs (ubuntu-x64, ubuntu-vulkan-x64, also macos-arm64 and win-cpu/win-cuda zips) DO ship ggml-rpc-server (the tool was renamed from rpc-server; the executable is ggml-rpc-server / ggml-rpc-server.exe) plus libggml-rpc, because release.yml sets CMAKE_ARGS "-DGGML_RPC=ON" for all jobs and tars the whole build/bin. But there is NO Linux CUDA release asset at all: Linux assets are CPU (GGML_BACKEND_DL with ~15 CPU variant .so files), Vulkan, SYCL, OpenVINO. Linux + CUDA + RPC therefore means building from source (or an in-house container). The official Docker images are CUDA 12.8.1 (tags *-cuda) and 13.3.0 (*-cuda13), built WITHOUT GGML_RPC (cuda.Dockerfile's cmake line has no -DGGML_RPC=ON; GGML_RPC defaults OFF) and light/server targets copy only llama/llama-cli/llama-completion or llama/llama-server — so no official image provides ggml-rpc-server, and llama-server inside them cannot use --rpc ("failed to find RPC backend"). 3. Building. tools/rpc/README.md (the only RPC build doc — docs/build.md has no RPC section): cmake -DGGML_CUDA=ON -DGGML_RPC=ON on each worker; the main host must ALSO be built with -DGGML_RPC=ON plus its own local backends. docs/build.md: cmake -B build -DGGML_CUDA=ON builds for the attached GPU (GGML_NATIVE -> CMAKE_CUDA_ARCHITECTURES=native when CUDA>=11.6 and CMake>=3.24); -DGGML_NATIVE=OFF for a cover-all build; -DCMAKE_CUDA_ARCHITECTURES="86;89" to pin; -DCMAKE_CUDA_COMPILER=/opt/cuda-X/bin/nvcc (+rpath) to pick a toolkit. ggml-cuda CMake needs CMake>=3.18 and fails hard if no CUDA toolkit. No explicit minimum toolkit version is enforced; code has CUDART_VERSION>=11070/11080/12000 feature gates. 4. GTX 970 (Maxwell, cc 5.2) on driver 535 / CUDA 12.2. (a) llama.cpp's non-native default arch list includes 50-virtual (PTX only) ONLY when the toolkit is <13 (comment: "50 == Maxwell, lowest CUDA 12 standard"); CUDA 13 builds cannot target it at all. (b) NVIDIA: CUDA 12.x "will continue to support building applications for these architectures"; CUDA 13.0 "Offline compilation and library support for these architectures have been removed". (c) Driver math: CUDA 12.2 GA's bundled driver is 535.54.03; minor-version compatibility lets any 12.x toolkit run on >=525.60.13 (<580) EXCEPT "Applications that compile device code to PTX will not work on older drivers" and it "requires passing the target architecture argument to NVCC (-arch=sm_xx)". Consequence: on the hub, either build with the 12.2 toolkit that matches driver 535, or with any 12.x toolkit but pass -DCMAKE_CUDA_ARCHITECTURES=52-real (SASS, not PTX). Forward-compat packages are Data-Center/NGC-RTX/Jetson only, so CUDA 13 on a GTX 970 with driver 535 is not an option; CUDA 13.x needs driver >=580 (13.1 GA >=590.44.01). (d) Performance: Maxwell is below GGML_CUDA_CC_DP4A (610) so MMQ int8 kernels are unavailable and below PASCAL so mul_mat_vec fusion is disabled — it works via the slower generic/cuBLAS paths. The RTX 3050 (cc 8.6, CUDA 13.1) and RTX 2070 Super (cc 7.5) are in every default list. 5. rpc-server at this tag: flags are -h, -t/--threads N (default hardware_concurrency/2), -d/--device <list>, -H/--host (default 127.0.0.1), -p/--port (default 50052), -c/--cache; there is NO --mem flag any more. Binding to anything but 127.0.0.1 prints the upstream banner "Never expose the RPC server to an open network! This is an experimental feature and is not secure!"; README says "Never run the RPC server on an open network or in a sensitive environment!". Transport is raw IPv4 TCP (AF_INET), no TLS/auth/proxy; server -H must be a dotted IPv4 literal (inet_addr); client --rpc host:port resolves via gethostbyname (MagicDNS names OK). Protocol is 5.1.0; client refuses a server with a different major or a higher minor — run the same build everywhere. ## Main-session notes

- Install path for Phase 1 (from S-02): release tarball `llama-<tag>-bin-ubuntu-vulkan-x64.tar.gz` per node, pinned tag (b10581 verified), extracted under the service user; CUDA builds only if Vulkan throughput disappoints (then per-node CUDA 12.x on the hub, 13.x elsewhere — see R01-F27…F30).
- Worker VRAM cannot be capped server-side at b10581 (no `--mem`): bound it with model choice, `-ts`/`-ngl` on the host, and `-d Vulkan0` device selection; recorded in the Phase 1 spec and ADR-0005 notes.
- Acceptance must check the `llama-bench`/`llama-server` backend string contains `RPC` and the worker log shows `Accepted client connection` — otherwise the run silently fell back to local.
- Worker processes as `systemd-run --user --unit=…` (transient service) or proper user units with linger (hub linger is off until Phase 0 step 2).
- **ADR-0006 (topology) observation, recorded 2026-08-31 — not yet a decision.** S-04 found the
  bottleneck is not the split but the *client*: whichever node runs `llama-bench`/`llama-server`
  must hold the GGUF and stream every remote shard out of its own uplink, and it memory-maps the
  whole file while doing so. On this fleet that node is the hub, whose measured send ceiling is
  5.0 MB/s (vs 16.3 MB/s peer-to-peer) and which also serves Plex, Immich and 14 other
  containers. CLAUDE.md §3.2 assigns `llama-server` there. Two mitigations are already proven
  (`-lm dio` to remove the page-cache footprint; `-dev` to keep the hub's GPU out of the split),
  but the load-time uplink cost is structural. **Wire the hub before deciding** — a wired hub may
  dissolve the question entirely, and writing ADR-0006 against a Wi-Fi measurement would settle
  the wrong problem.

## Recommendations for the spec

1. Pin llama.cpp to a single tag for the whole fleet and record it in the spec as 'v0.2.0 (= b10566)'; RPC protocol 5.1.0 mismatch across builds is a hard failure, so every node's ggml-rpc-server and the hub's llama-server must come from the same tag (F1, F10).
2. Linux CUDA nodes must build from source: cmake -B build -DGGML_CUDA=ON -DGGML_RPC=ON (add -DGGML_NATIVE=OFF or an explicit CMAKE_CUDA_ARCHITECTURES when building on one box for another). Do not plan on the official Docker images or the ubuntu release tarballs for GPU RPC workers — the tarballs are CPU/Vulkan only and the images lack the RPC backend (F3, F4, F7). The CPU/Vulkan tarballs are still useful for a quick no-GPU smoke test (they do contain ggml-rpc-server).
3. Hub (GTX 970, driver 535): build with the CUDA 12.2 toolkit that matches driver 535, or with any 12.x toolkit plus -DCMAKE_CUDA_ARCHITECTURES=52-real so Maxwell gets SASS rather than PTX (F17, F21, F23, F24). Never install CUDA 13 on that box for this purpose (needs driver >=580 and cannot target cc 5.2). Treat the 970 as a 'fits, but slow' device (no MMQ/dp4a, F18) — primarily extra VRAM for the split, and consider the Vulkan backend as a fallback experiment if the CUDA 12.2 build fights the host toolchain.
4. RTX 3050 node on CUDA 13.1: default arch list covers 86-real; requires driver >=590.44.01 (F22). RTX 2070 Super (cc 7.5) is covered by every default list. Keep per-node builds native (GGML_NATIVE on) since each node compiles its own ggml-rpc-server.
5. Write the rpc-server unit as: ExecStart=.../ggml-rpc-server -H <node's Tailscale IPv4> -p 50052 [-c] [-d CUDA0]; -H must be a dotted IPv4 literal (F10) and the upstream 'not secure' banner will print and is expected (F9). Add the spec sentence that the RPC server is unauthenticated raw TCP and the tailnet is the only boundary; combine with Tailscale ACLs limiting port 50052 to the hub.
6. Resolve the hub's Tailscale userspace-mode problem before Phase 1 (F29, F30): either switch solarplexus to kernel/tun mode, or run llama-server on a tun-mode node and keep the hub as a worker only after confirming it can accept inbound tailnet TCP. This is an ADR-worthy decision (topology ADR 0006 is reserved).
7. llama-server on the hub: --host <tailnet IPv4> --port 8080 --rpc <worker1>:50052,<worker2>:50052 -ngl auto (default) and let the default free-memory split do the work; only add -ts if the split is bad. Use --list-devices first to confirm RPC<n>[host:port] devices appear (F11, F12). Keep logging at default -lv 3 and never use -v or --log-prompts-dir in service units (F14); consider --no-slots and leave --metrics/--props off unless needed; optionally --log-file to a member-readable location for the thank-you board.
8. Benchmark the split with llama-bench --rpc <servers> -ngl 99 before committing to a model, since RPC exists to fit, not to speed up (F15).
9. Service user: run ggml-rpc-server as a dedicated non-root user under a user manager with loginctl enable-linger and the unit in ~/.config/systemd/user (F27, F28); verify ls -l /dev/nvidia* shows 0666 (F25) and, if a distro has tightened it, add the user to the group named by the device GID rather than changing module parameters. Set LLAMA_CACHE (or let it default to ~/.cache/llama.cpp/rpc) to a disk with room for the cached tensors when using -c.
10. Credit rows: llama.cpp row already exists; add the release/tag convention and the RPC maintainer handle (rgerganov) to docs, and add Tailscale userspace-mode note to the hub's page.

**Completeness critic — missing for a plan writer:**

- Argument-order sensitivity of --list-devices / -dev / -mmdev relative to --rpc: at b10581 `--list-devices` prints and exit(0)s inside its parse handler (common/arg.cpp ~L2727) and `-dev` resolves names at parse time, so `llama-cli --list-devices --rpc H:P` (S-03's command) and `-dev RPC0` placed before `--rpc` cannot see RPC devices. The dossier's rec 7 and spec acceptance #1 assume the opposite. Missing: a verified fact that `--rpc <servers>` must precede `--list-devices`/`-dev`, the exact -dev names (RPC0, RPC1 ... global counter per F10), and the corrected acceptance command.
- Silent local fallback, precisely: ggml_backend_rpc_get_device_count() logs `Failed to connect to <endpoint>` and returns 0, so add_rpc_devices registers a zero-device RPC registry and llama-server/llama-bench proceed locally with no error and no flag to make a missing endpoint fatal. Missing: that greppable log line, confirmation that no `--rpc-required`-style option exists, and a recommended ExecStartPre/TCP-probe gate for the host unit (needed for the reboot case where llama-server starts before the workers).
- Mid-run worker loss: every RPC send/recv failure hits RPC_STATUS_ASSERT -> GGML_ABORT("Remote RPC server crashed or returned malformed response") so llama-server dies with SIGABRT (Restart=on-failure fires), but transport.cpp sets only TCP_NODELAY/SO_REUSEADDR (no SO_KEEPALIVE, SO_RCVTIMEO) so a worker that vanishes without FIN/RST (laptop lid closed, Wi-Fi drop) hangs llama-server indefinitely; and get_socket() caches one socket per endpoint for the process lifetime, so a restarted worker is never re-dialled without restarting llama-server. The spec's 'worker drops mid-run' row is still UNVERIFIED; a watchdog/health-timer design and StartLimitIntervalSec/StartLimitBurst values for the crash-restart loop are missing.
- ggml-rpc-server concurrency model: the serve loop is serial (accept -> rpc_serve_client -> next accept; listen backlog 1) and the client holds its socket for its lifetime, so each worker serves exactly one llama-server/llama-bench at a time and a second client blocks in the accept queue; all buffers a client allocated are freed on its disconnect (~rpc_server). Missing from the facts; it is why 'stop the host unit before llama-bench' is required and it constrains Phase 2 (no two models/servers can share a worker).
- supports_op on the RPC device returns true unconditionally (ggml-rpc.cpp ~L1913, to-do), so the scheduler never falls back to the hub CPU for an op the remote Vulkan backend lacks; the worker aborts instead and the hub sees 'Remote RPC server crashed'. Missing: whether ggml-vulkan at b10581 implements every op of the Phase 1 model (Qwen3.8-27B hybrid linear-attention/gated-delta ops) and the backups, and how `-fa auto` resolves over RPC -- this is the concrete form of the spec's 'if hybrid layers misbehave over RPC' risk and decides the smoke-test order.

Missing: this ordering, its -mg consequence, and a worked mapping from the spec's per-node VRAM caps (7/5/3.5 GB) to -ts proportions given that F12's split is by layer COUNT (hybrid layers differ in size) plus per-device compute/KV buffers; also that the default free-memory split is recomputed at every start, so GB-per-node is nondeterministic unless -ts is set.

- llama-server flags the Caddy /chat route depends on: `--api-prefix PREFIX` (LLAMA_ARG_API_PREFIX), `--webui/--no-webui`, `--webui-config`, `-a/--alias` exist at b10581 but are not in F13; missing whether the built-in UI works under a reverse-proxied sub-path (the plan hedges between handle and handle_path) and what model name /v1/models returns for the curl test.
